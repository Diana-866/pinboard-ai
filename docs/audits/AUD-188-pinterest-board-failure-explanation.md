# AUD-188 — Понятное объяснение недоступной Pinterest-доски

**Дата:** 2026-11-08  
**Область:** API расписания и карточка публикации в календаре  
**Статус:** изменения внесены в feature-ветку; production не затронут.

## Проблема

После безопасной блокировки повторов при удалённой/недоступной Pinterest-доске пользователь видел только общий статус «Ошибка». Сервер уже сохранял диагностическое сообщение в `pin_schedules.last_error`, но клиент не получал отдельный безопасный код причины, а показывать необработанный текст провайдера в интерфейсе было бы нежелательно.

## Исправление

- Добавлен helper `getScheduleFailureReason`, который распознаёт только известные сообщения о недоступной/неподтверждённой доске и возвращает ограниченный код `board_unavailable`.
- GET `/schedule` добавляет поле `failure_reason`; сырые тексты ошибок не используются для формирования UI-сообщения.
- Frontend сохраняет код причины в модели расписания.
- Карточка неудачной публикации показывает отдельное предупреждение на семи поддерживаемых языках (ru, en, de, es, fr, pt, zh): доска удалена или доступ потерян; PinPosy не будет повторять публикацию на ней; нужно выбрать доступную доску и создать новое расписание.
- Предупреждение не включает кнопку опасного повтора и не меняет сохранённый board ID.

## Проверки

- Изолированно выполнены 4 Node.js assertions для определения причины:
  - оба известных сообщения о недоступной доске дают `board_unavailable`;
  - произвольная техническая ошибка не раскрывается и не классифицируется как board issue;
  - неудачный текст в неактивном расписании не отображается как причина текущей ошибки.
- Добавлен полноценный regression test в `backend/test/pinterest-schedule.test.js`, но весь файл и backend suite в этой сессии не запускались.
- Frontend build/typecheck не запускались; визуальное поведение не проверено в браузере.

## Границы

- Исправление только объясняет причину и направляет пользователя к новому расписанию; автоматическая замена доски не выполняется.
- Нет изменений в Pinterest API, OAuth, таблицах или миграциях.
- Production, Supabase и реальные расписания не затрагивались; деплой и merge не выполнялись.
