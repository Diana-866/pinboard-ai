# AUD-237 — конкурентный захват Pinterest-расписаний (2026-11-09)

## Что проверено
- Worker запускается через внутренний endpoint и забирает задания только через PostgreSQL RPC `claim_due_pin_schedules`.
- Актуальная функция (migration 092) выбирает готовые строки с `FOR UPDATE SKIP LOCKED`, переводит их в `publishing`, увеличивает `attempts` и назначает новый случайный `claim_token`.
- Последующие изменения worker подтверждают полный identity расписания и текущий `claim_token`; завершение публикации дополнительно фиксируется транзакционной RPC.
- Поэтому добавлять process-local mutex как замену DB coordination не нужно: он не защитил бы несколько Render instances, а DB claim уже является общей точкой синхронизации.

## Улучшение
- Добавлен `backend/test/pinterest-schedule-claim-concurrency.sh`.
- Тест создаёт два due schedule, удерживает блокировку первой строки и одновременно запускает два независимых PostgreSQL worker-вызова с batch size 1.
- Ожидается, что оба вызова не заберут одну запись: только один получит вторую доступную строку, другой вернёт пустой результат. После снятия блокировки следующая попытка забирает первую строку.
- Финальная проверка требует для обеих строк `publishing`, ровно одну попытку, непустые и разные fencing tokens.
- Скрипт подключён к `.github/workflows/atomic-payment-integration.yml` после существующего Pinterest publication concurrency test.

## Пользовательский эффект
Если два экземпляра PinPosy проснутся одновременно, одна и та же запланированная публикация не должна попасть в обработку обоих экземпляров. Каждая строка очереди получает одного владельца и отдельный токен; временно заблокированная строка не мешает второму worker обработать следующую доступную.
