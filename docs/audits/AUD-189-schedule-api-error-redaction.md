# AUD-189 — Удаление внутренних ошибок Pinterest из клиентского API

**Дата:** 2026-11-08  
**Область:** backend GET /schedule и сериализация расписаний  
**Статус:** изменения внесены в feature-ветку; production не затронут.

## Проблема

GET /schedule использовал `select("*")` и возвращал строки расписания практически без фильтрации. Поле `last_error` содержит внутреннюю диагностику worker/Pinterest и могло попасть в браузер, хотя интерфейс использует только безопасный код `failure_reason`. Сырые сообщения провайдера не должны становиться частью публичного API-контракта.

## Исправление

- Добавлен pure helper `sanitizeScheduleForClient` в `backend/pinterestSchedule.js`.
- Helper удаляет только `last_error`, сохраняя остальные поля расписания и рассчитанные UI-поля (`retryable`, `retry_reason`, `failure_reason`).
- Все три ветви GET /schedule используют санитайзер: обычный ответ, ошибка загрузки metadata и штатное обогащение failed rows.
- Исходный объект не мутируется; поле остаётся в базе для внутренней диагностики и поддержки.
- Добавлен regression test, который проверяет отсутствие `last_error` в клиентском объекте, сохранение безопасных полей и неизменность исходной строки.

## Проверки

- Код helper и маршрута перепроверен после записи в GitHub.
- Полный backend test suite, отдельный Node test-файл и frontend build/typecheck в этой сессии не запускались.
- Production API и Supabase не вызывались; миграции, deploy и merge не выполнялись.

## Следующий шаг

Отдельно прорабатывается безопасная смена Pinterest-доски у failed schedule. Она должна быть атомарной и разрешаться только при подтверждённо безопасном исходе публикации; нельзя менять board ID, если удалённая публикация могла состояться.
