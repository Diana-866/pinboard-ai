# AUD-165 — Pinterest publication lifecycle and concurrency audit

**Branch:** `feat/persisted-boards-api`  
**Reviewed HEAD:** `88b90815381544f211409c5d1f4291bd32c557b9`  
**Scope:** schedule claim → durable attempt journal → Pinterest create request → local completion; stale-worker recovery; manual positive-evidence reconciliation.  
**Change type:** audit only. No production calls, database writes, migrations, or provider requests were performed.

## Executive result

No confirmed path was found in the reviewed state machine that automatically re-sends a Pinterest create request after an ambiguous outcome. The implementation is deliberately fail-closed: it persists a journal before the external POST, treats transport/timeout/provider-server uncertainty as non-retryable, and requires positive evidence for operator reconciliation.

The most important remaining verification limitation is that the repository's SQL integration tests exercise many state transitions and inspect lock ordering, but do not appear to run competing transactions concurrently against a live PostgreSQL instance. Therefore this is a code/schema audit, not a proof under real database contention.

## Lifecycle trace

1. **Claim.** `claim_due_pin_schedules` bounds claims to at most 10, uses `FOR UPDATE SKIP LOCKED`, increments the schedule attempt counter, and issues a fresh `claim_token`. A stale claim is fenced by clearing/rotating the token before the schedule can be claimed again.
2. **Pre-POST reservation.** Scheduled work enters `begin_scheduled_pinterest_publish`. The current definition locks the Pinterest account before the schedule, verifies the exact schedule ID, owner, pin, account, board, status and claim token, then delegates to `begin_pinterest_publish_v2`. The durable attempt row is created before the HTTP request.
3. **Duplicate prevention.** The account-scoped attempt journal is unique for a pin/account pair. Existing `processing` or `unknown` attempts do not start another create request. A retry is allowed only for a `failed` attempt explicitly marked `retry_safe=true`; consuming that retry clears the marker.
4. **External request.** The worker calls Pinterest `POST /pins` with rate-limit retry disabled. Network failures, timeouts, HTTP 408/429/5xx, missing remote IDs, and failures to persist a returned remote ID are treated as ambiguous and do not become automatically retryable.
5. **Completion.** `complete_pinterest_publish_v2` locks account → all matching active/uncertain schedules in stable order → attempt. It verifies the reserved board and remote publication identity, then records the publication, marks the attempt published, and reconciles matching publishing/unknown schedules in one transaction.
6. **Stale recovery.** A stale publishing schedule with a published journal is reconciled to published. A stale schedule with a failed journal is requeued only if that journal explicitly says `retry_safe=true`. A schedule with a processing/unknown journal becomes unknown; a schedule with no journal can safely be requeued because the worker cannot cross the external-POST boundary without first creating the journal.
7. **Operator reconciliation.** Migration 082 accepts only an old unknown schedule and old unknown/processing attempt, with no claim token, exact owner/account/board/remote identity checks, and `retry_safe=false`. It records an append-only audit receipt and marks the publication as published. It has no non-publication action and does not enable retry.

## Concurrency and race review

| Race | Guard found | Assessment |
| --- | --- | --- |
| Two workers claim the same due schedule | Row locks with `SKIP LOCKED`, fresh claim token | Guarded |
| Old worker resumes after stale recovery | `begin_scheduled_pinterest_publish` requires the exact current claim token | Guarded before journal reservation |
| Recovery runs before a worker reserves its journal | Schedule row lock serializes claim validation/reservation against stale recovery | Guarded |
| Worker crashes after journal reservation / before response | Existing processing journal becomes unknown; no automatic retry | Fail-closed |
| Pinterest creates a pin but response is lost | Transport/timeout outcome becomes unknown; no automatic retry | Fail-closed; operator verification required |
| Worker returns after schedule became unknown | Completion RPC can persist a confirmed late success and reconcile unknown | Guarded by account/schedule/attempt locks and identity checks |
| Manual reconciliation races with a live worker | Reconciliation requires stale unknown state; it locks account → schedule → attempt and checks current state under lock | State transitions serialize; genuine external evidence remains a human responsibility |
| Conflicting remote pin or board identity | Completion/reconciliation rejects conflicting identity instead of overwriting it | Guarded |
| Disconnect races with scheduled reservation | Account-first lock order is shared by reservation, completion, and account-scoped operations | Lock order is consistent in reviewed definitions |

## Findings and limitations

### AUD-165-01 — No automatic retry path found for ambiguous publication outcomes

The reviewed SQL and JavaScript preserve the durable attempt as the authority. Unknown outcomes are blocked from both automatic and manual retry; only explicit safe rejection evidence can set `retry_safe=true`. This is the correct duplicate-avoidance posture for a create API where the client cannot prove whether a timed-out request was accepted.

### AUD-165-02 — Concurrency verification is not equivalent to a live race test

The integration SQL covers claim fencing, stale recovery, account scoping, retry-safe behavior, disconnect interactions, completion identity checks, and reconciliation guards. Some assertions inspect function-definition lock order. I did not find a test that launches competing database sessions and deliberately interleaves worker completion, stale recovery, disconnect, and operator reconciliation. A future test harness should exercise those races against PostgreSQL, not just run the SQL fixtures sequentially.

### AUD-165-03 — Pinterest's remote create operation has no local exactly-once guarantee

The local journal prevents PinPosy from intentionally issuing a second create request after an ambiguous result. It cannot roll back a remote pin or guarantee exactly-once behavior across a network boundary. The operational policy must remain: unknown means inspect Pinterest and reconcile only with positive evidence; never infer non-publication merely from a missing local confirmation.

### AUD-165-04 — Redundant worker completion UPDATE removed

The audit found that `publishPin` calls `complete_pinterest_publish_v2`, which already atomically marks matching active/uncertain schedules as `published`, stores the remote pin ID and clears the claim token. The worker then attempted a second conditional UPDATE requiring the old `status='publishing'` and old claim token. That predicate is already false after the completion RPC, so the second UPDATE normally affected zero rows while the worker still reported success.

**Resolved on this branch:** the redundant worker UPDATE has been removed. The completion RPC is now the single authoritative transition. The PostgreSQL integration fixture was strengthened to assert that completion stores the remote ID, sets `published_at`, clears `claim_token`, and leaves failed historical schedules unchanged. The SQL test has not yet been executed in this audit.

### AUD-165-06 — Disconnect after reservation does not cancel a prepared POST

**Finding: documented race window; no claim of hard cancellation.** The SQL reservation and disconnect operations serialize on the Pinterest account row. If disconnect commits first, the reservation rejects and no attempt is created. If reservation commits first, the attempt is durable and the reservation transaction releases its account lock before the external request.

The backend then calls `withAccount()`, which re-reads the active account and obtains the token before calling `executeWithAccountToken()`. This blocks the common case where disconnect has already committed before that read. However, there is still a time-of-check/time-of-use interval between the active-account read/token selection and the actual `POST /pins`. A disconnect can commit in that interval; the already-read token can still be passed to the HTTP handler. The disconnect RPC clears credentials in PinPosy and fails future queued schedules, but does not revoke the provider token at Pinterest.

Therefore the actual guarantee is narrower than “disconnect cancels every not-yet-sent publish”: disconnect that wins before reservation prevents the attempt; disconnect after reservation prevents later account reads and future queued work, but cannot guarantee cancellation of a request whose token has already been read or whose HTTP request is already in flight. The durable attempt journal still prevents an ambiguous request from being automatically replayed.

**Disposition:** no code change made in this audit. Holding a database row lock across a remote HTTP request would make provider latency/timeout part of a database transaction and is not an acceptable default fix. A final pre-send state check can shrink, but cannot eliminate, the race. If product semantics require strict cancellation, design a separate revocation/cancellation protocol and define its linearization point; do not describe local disconnect as an atomic cancellation of external publication. UI/help text should say that a publication already starting may still complete after disconnect.

**Coverage note:** `backend/test/pinterest-account-publication.integration.sql` verifies the disconnect-first case (disconnect commits, then reservation is rejected) and verifies that disconnect leaves an already-publishing schedule for journal reconciliation. It does not test or prove cancellation after the backend has read the access token. The concurrency harness currently covers completion/reconciliation and completion/stale-recovery races, not this external HTTP boundary.


### AUD-165-07 — OAuth reconnect after disconnect and stale callback fencing

**Finding: no credential-resurrection path identified in the reviewed SQL flow.** OAuth attempts are single-use and generation-fenced per PinPosy user. `begin_pinterest_oauth_attempt` increments the durable generation and replaces the current attempt ID. The callback exchanges the provider code and fetches the Pinterest profile before persistence, but the final `commit_pinterest_oauth_attempt_v2` locks the OAuth connection-state row and verifies generation, attempt ID, token version, expiry, and current user/session version before writing credentials. A stale callback therefore cannot commit after a newer attempt or disconnect has invalidated its generation.

`disconnect_pinterest_account_v2` also updates the same per-user OAuth state row, increments generation, clears the active attempt, deletes the account refresh lease, and then clears the account credentials. This uses the same state-row serialization point as the callback. If callback commits first, the later disconnect clears the credentials; if disconnect wins first, the callback sees a stale generation and cannot restore them. The existing `backend/test/pinterest-oauth-concurrency.sh` exercises both contenders waiting on the shared state-row lock and verifies that the final account remains disconnected with null credentials and no active OAuth attempt.

Reconnect of the same Pinterest identity is intentionally supported: `commit_pinterest_oauth_attempt_v2` upserts by (user_id, pinterest_user_id), reactivating the stable row. The integration fixture checks that reconnect returns the same account ID. Missing replacement refresh token/expiry are preserved rather than overwriting known values with null. Refresh-token rotation uses a separate account-scoped lease and fencing checks; the fixtures cover stale refresh completion after disconnect and reconnect during an in-flight refresh.

**Scope and caveats:** the OAuth generation is per PinPosy user, not per Pinterest account. Starting a new OAuth attempt or disconnecting one account invalidates any other in-flight OAuth attempt for that user. This is consistent with the schema comment and “one in-flight link attempt at a time” design, but it should remain explicit in product behavior. Provider authorization-code exchange and profile lookup happen before the final database fence; an invalidated callback may still consume a one-time code or make a read-only profile request, but cannot persist credentials. The local disconnect flow clears PinPosy credentials; it does not demonstrate that Pinterest's own provider-side authorization has been revoked.

**Disposition:** no code change made. Existing SQL and shell regression coverage is relevant, but its actual CI execution is still unconfirmed. Do not claim the race test passed until a runner executes it successfully.

### AUD-165-10 — Expired Storage deletion claim can reopen an object path

**Regression coverage:** the PostgreSQL integration fixture now asserts that an expired deletion claim becomes quarantined, the stale worker token cannot finalize it, and neither upload nor another delete claim can reuse it. ### AUD-165-13 — Prodamus payment refunds have no implemented lifecycle

**Finding confirmed in the reviewed branch:** Prodamus payment creation is implemented for subscriptions (backend/billing.js) and credit packs (backend/creditsBilling.js), while backend/prodamus.js exposes payment-link creation and webhook-signature/status/amount helpers only. It contains no provider refund request, refund lookup, or refund reconciliation operation. The payment-facing routes in backend/index.js create orders, return user purchase history, expose billing health, and list subscriptions for admins; no Prodamus refund or payment-compensation route is registered.

**Webhook behavior:** normalizePaymentStatus recognizes only success, order_canceled, and order_denied. An unrecognized status is recorded through billing_webhook_exceptions with reason unsupported_payment_status and returned as ignored/review-required. This provides a durable exception trail, but it does not change a successful payment, revoke a subscription, or reverse a credit grant. The existing guards correctly prevent a late cancellation callback from overwriting a successful subscription or credited purchase; they do not constitute refund handling.

**Schema and fulfillment effects:** migration 006 constrains subscription status to pending/success/canceled/denied/expired; migration 007 constrains credit purchase status to pending/success/canceled/denied. There is no refunded payment state or Prodamus refund journal in the reviewed migration chain. Migration 010 records a positive purchase-linked top-up and the balance_credited_at marker atomically; no matching payment-refund compensation RPC was found. Migration 011 activates a paid period and updates the effective user tariff; no payment-refund entitlement-reversal RPC was found. Thus a refund performed outside PinPosy after successful fulfillment would leave internal credits/entitlement unchanged unless handled manually through a separate process.

**Scope clarification:** provider_refund_reconciliation_audit (073) and provider_refund_operator_actions (078), plus the four /admin/provider-refunds/* routes, reconcile GPTunnel generation/regeneration provider charges and failed generation reservations. Their keys and target records are generation requests/tasks, not Prodamus provider_payment_id, subscriptions, or credit_purchases. They must not be reused as a Prodamus payment-refund mechanism.

**Risk:** an operator can potentially refund a customer in the payment provider's external interface without a corresponding PinPosy state transition. The customer could retain already-credited credits or an activated paid period. Conversely, automatically reversing a credit balance or resetting a user's tariff without checking the provider's confirmed refund and later purchases could corrupt the ledger or revoke a newer entitlement. The repository review does not establish whether operators currently perform external refunds or whether the Prodamus merchant account exposes a specific API for them.

**Recommended next design (not implemented):** add a separate Prodamus payment-refund workflow only after verifying the merchant's supported refund interface and callback contract. It should have an immutable, idempotent refund/action ID tied to the original provider payment ID; explicit states for requested, confirmed, failed, and unknown provider outcome; an append-only operator/evidence journal; and transactionally guarded internal compensation. Credit refunds should append a compensating ledger entry rather than edit/delete the original top-up, with a documented policy for already-spent credits. Subscription refunds should preserve payment/period history and revoke entitlement only under an explicit policy that checks for later successful purchases. Ambiguous provider outcomes must go to reconciliation, not trigger blind retries or automatic compensation.

**Verification and scope:** inspected payment routes, Prodamus helper exports, both webhook handlers, the purchase/subscription schema constraints, fulfillment RPCs, relevant tests, and the GPTunnel operator-refund implementation. This is a source audit, not a live merchant-account or Prodamus-dashboard inspection. No refund was initiated; no payment, credit balance, subscription, production database, or external service was changed. No CI result is implied.


### AUD-165-14 — Official Prodamus refund procedure is merchant-dashboard driven in the public documentation

**Official documentation reviewed:** Prodamus describes refunds as a merchant-initiated request in the payment-page account, under Payment list → select order ID → create full or partial refund request. The documented minimum refund amount is 100 RUB. The merchant chooses either deduction from future incoming payments (the request is canceled if sufficient funds do not accumulate within 10 days) or a payment order funded by a manual bank transfer. Partial refunds may require Prodamus support to enable the feature for the payment page.

**Provider lifecycle:** after submission the payment/order is shown as “Возвращается” (refund requested/in progress). “Возвращён” means Prodamus has fulfilled its refund obligation and issued the refund receipt; the bank may take 1–30 business days to credit the payer (usually 1–5). Prodamus says the merchant can track refunds in the account and receives an email notification at the payment-page notification email address. Therefore a submitted request, a pending request, and a completed refund are distinct states.

**API/webhook documentation boundary:** the public self-integration REST documentation reviewed describes payment-link generation and the payment notification URL (urlNotification) for payment events. It does not document a refund-creation endpoint, refund-status lookup endpoint, or refund webhook/callback contract. The public refund instructions instead direct merchants to the account UI and describe status tracking there plus email notification. This is a statement about the reviewed public documentation, not proof that Prodamus has no private, account-specific, or newly released API. Confirm API and webhook availability directly with Prodamus support before implementing any automated provider-side refund operation.

**Implication for PinPosy MVP:** until Prodamus confirms a supported API/callback, use a controlled manual-provider workflow: (1) admin opens a refund case in PinPosy, linked to exactly one internal payment and provider order ID; (2) case is marked requested only after an operator submits the request in Prodamus; (3) entitlement/credits are not automatically reversed while provider status is “Возвращается”; (4) operator records provider evidence and confirms only after seeing “Возвращён” in the provider account and retaining the refund reference/receipt; (5) one idempotent database transaction posts the internal compensation and marks the refund case completed. If the provider request is canceled or rejected, no compensation is posted. If status/evidence is ambiguous, case remains under review and no blind retry occurs.

**Financial policy decisions still required before implementation:** define whether partial refunds are allowed for digital credit packs and subscription periods; how partial refund amounts map to credits or remaining entitlement; what happens when purchased credits were already spent; and how a refunded older subscription interacts with later successful subscriptions. For credit packs, keep the original positive ledger row and append a compensating negative entry; do not delete or rewrite financial history. For subscriptions, preserve the original paid period and payment history; any entitlement reduction must be derived from an explicit policy and must not reset a later paid plan. Prodamus' minimum 100 RUB refund means a lower partial refund cannot be assumed available.

**Sources:** official Prodamus pages “Как в Prodamus устроены возвраты платежей клиентам”, “Как сформировать заявку на возврат”, “Как понять, что возврат произведён”, and “Документация для самостоятельной интеграции сервисов”.

**Verification and scope:** documentation was reviewed on 2026-11-08 and compared with the current PinPosy branch implementation. No merchant account was accessed, no request was submitted, no payment was refunded, no provider credentials were used, and no production or external state was changed.


### AUD-165-15 — Admin dashboard financial aggregates are not payment/entitlement metrics

**Finding confirmed:** `backend/admin.js::getStats` builds `creditsSoldByMonth` by summing every positive `credit_transactions.amount` row, without filtering by transaction type or linking the row to a successful `credit_purchases` record. The repository's own development top-up path writes positive ledger adjustments with type `topup` (`backend/index.js` → `backend/credits.js::adjustBalance`), so this aggregate includes non-sale credits. It measures positive credit-ledger movements, not paid credit-pack sales and certainly not RUB revenue. The field name `creditsSoldByMonth` is therefore materially misleading.

**Second metric limitation:** `tariffPlanBreakdown` counts the cached `users.tariff_plan` field and does not resolve active paid entitlements or expiry. The implementation comment explicitly notes that it is a count of cached tariff labels, not effective active entitlements. **Finding confirmed:** `callPinterest()` in `backend/pinterest.js` returns only `{ ok, status, data }` and discards the HTTP response headers. `executeWithAccountToken()` in `backend/pinterestAccountRequest.js` handles one HTTP 429 retry by waiting a hard-coded 2,000 ms, then retries once. The helper receives no `Retry-After` or Pinterest `x-ratelimit-reset` value, so it cannot wait for the provider's indicated reset time. This behavior applies to operations using the default `retryRateLimit: true` path, including safe reads and board verification.

The non-idempotent `POST /pins` path explicitly passes `retryRateLimit: false`, so a 429 is not replayed automatically. That is a deliberate duplicate-avoidance safeguard and should remain unless the provider's response semantics and idempotency guarantees are established. However, the scheduled worker then treats 429 as an unknown publication outcome and does not automatically reschedule it; this preserves safety but may require operator reconciliation rather than a timed retry.

**Impact classification:** premature retry and avoidable rate-limit pressure for read requests; conservative but potentially operationally sticky handling for publish 429s. Not evidence of duplicate Pinterest publications.

**Recommended remediation (not implemented):** preserve response headers in the Pinterest response wrapper; parse and validate `Retry-After` (seconds or HTTP date) and `x-ratelimit-reset`; use a bounded provider-directed wait with jitter and a safe fallback when headers are absent or malformed. For scheduled writes, do not blindly replay a create request after 429: retain the unknown-outcome fence and add a reconciliation/explicit operator workflow, or only enable retry after Pinterest's response contract proves that the request was rejected before creation. Add tests for reset headers, malformed/missing values, bounded waits, and the invariant that non-idempotent publish is not replayed.

**Evidence:** inspected `backend/pinterest.js::callPinterest`, `withAccount`, the `publishPin()` `retryRateLimit: false` call, `backend/pinterestAccountRequest.js::executeWithAccountToken`, and tests `backend/test/pinterest-account-request.test.js`. Existing tests assert the fixed 2,000 ms delay and that publication is not retried on 429; no test covers provider reset headers. Pinterest documents `x-ratelimit-limit`, `x-ratelimit-remaining`, and `x-ratelimit-reset` response headers and category-specific quotas in its official rate-limit reference: https://developers.pinterest.com/docs/reference/rate-limits/.

### AUD-165-29 — Pinterest publishing has no shared per-account provider pacing across worker instances

**Finding confirmed:** `claim_due_pin_schedules()` uses `FOR UPDATE SKIP LOCKED` and changes each selected row to `publishing` with a fresh claim token, so concurrent worker invocations do not claim the same schedule row. The worker processes each claimed batch sequentially, and the database claim fencing/stale recovery prevents a superseded worker from starting a new publication reservation. However, distinct schedules for the same Pinterest account can be claimed by different backend instances and published concurrently: the account row lock in `begin_scheduled_pinterest_publish()` is held only during the database reservation transaction and is released before the external Pinterest HTTP request. The `pinterestWorkerLimiter` uses express-rate-limit's default process-local MemoryStore and is keyed by IP because the worker has no authenticated user. The source comment explicitly says a shared store is required if the backend is scaled across instances.

Consequently, the database queue provides per-row exclusivity, not a global per-account/API request budget. Two or more backend instances can each pass their own worker limiter and concurrently issue writes for the same Pinterest user/app. There is no durable per-account lease, distributed token bucket, or queue-level serialization around the external `POST /pins` call. This is relevant because Pinterest applies category quotas: `org_write` is 300 requests/day for Trial access and 100 requests/minute per user/app for Standard access, in addition to universal limits. At present this is a scale-out risk rather than proof of a production outage; the observed deployment context previously described a single Render backend, and no live instance count was verified during this audit.

**Impact classification:** rate-limit exhaustion and bursty provider traffic if multiple backend instances or overlapping cron callers are active; not a same-schedule double-claim or duplicate-publication finding. The account-scoped publication journal still prevents a second create for the same local pin/account.

**Recommended remediation (not implemented):** introduce a durable per-account publication lease/queue or shared distributed limiter keyed by Pinterest account and API category; hold/renew the lease across the external request with a bounded timeout and fencing token, while preserving the existing account -> schedule -> attempt database lock order. At minimum, configure a shared express-rate-limit store for the worker endpoint and enforce a provider-aware per-account write budget in the worker itself. Add an integration test with two independent worker sessions claiming different schedules for one Pinterest account and assert that provider-write leases serialize them, while different accounts may proceed independently.

**Evidence:** inspected `backend/pinterestRateLimit.js`, the internal worker route and sequential loop in `backend/pinterest.js`, migrations `049`, `056`, `057`, `059`, `060`, and `061`, `backend/test/pinterest-account-publication.integration.sql`, `backend/test/pinterest-publication-concurrency.sh`, and `docs/pinterest/scheduler-setup.md`. Existing SQL tests exercise same-row claim fencing, late-success/stale-recovery, and publication/reconciliation lock races, but do not exercise concurrent provider writes for distinct pins on the same account across independent worker instances. Pinterest's official rate-limit documentation lists `org_write` quotas and the response headers used to monitor them: https://developers.pinterest.com/docs/reference/rate-limits/.

**Verification and scope:** static source, migration, test, and setup-document inspection only. No production database, live worker, Pinterest account, OAuth credential, or provider request was accessed. No application code, migrations, or production state were changed by this finding.


### AUD-165-30 — Pinterest due-queue selection has no deterministic tie-breaker or tenant fairness

**Finding confirmed:** the current `claim_due_pin_schedules()` definition (migration 060, retained by the later reviewed Pinterest migrations) selects eligible rows with `ORDER BY scheduled_at ASC FOR UPDATE SKIP LOCKED LIMIT ...`. It does not add a unique secondary ordering key such as `id`, `created_at`, or a tenant-fairness cursor. The SQL function clamps every claim batch to at most 10 rows. The worker processes each claimed batch sequentially, and the documented external cron invokes it approximately once per minute.

For schedules with equal `scheduled_at` values, the query does not define a deterministic order among tied rows. PostgreSQL documents that a `LIMIT` subset is unpredictable unless the ordering constrains rows to a unique order. With more than ten simultaneously due rows sharing a timestamp, the exact rows selected in a given batch are therefore not contractually stable. Separately, the queue is globally ordered by due time, not round-robin or capped per user/account: a tenant with a large block of older due work can occupy successive batches ahead of later-due work belonging to other tenants.

**Backlog consequence:** at the documented baseline of one cron invocation per minute and ten claimed rows per invocation, nominal drain capacity is at most 10 schedules/minute before accounting for provider latency, failures, or overlapping invocations. A backlog of 600 due rows therefore needs roughly 60 minutes to drain if no new work arrives and each invocation completes all ten. If the sustained arrival rate reaches or exceeds the effective processing rate, backlog latency will not converge. This is a capacity calculation from the configured batch/cadence, not a measured production throughput claim. The setup document currently says the endpoint is not yet configured in production, so no live backlog or customer impact was verified.

**Impact classification:** nondeterministic ordering within timestamp ties, no explicit cross-tenant fairness guarantee, and potentially long recovery latency after downtime or burst creation. Static inspection does not prove permanent starvation: older due rows remain eligible and are normally prioritized by their scheduled time. The finding is about bounded throughput and lack of fairness/deterministic tie-breaking, not loss of jobs or duplicate publication.

**Recommended remediation (not implemented):** add a unique stable tie-breaker (for example `ORDER BY scheduled_at ASC, id ASC`) and index the matching eligibility/order path. Define a per-user/account fairness policy if one tenant must not monopolize a shared worker (for example, per-tenant subqueues or a rotating tenant cursor with a bounded number of claims per tenant). Make worker capacity configurable and observable; expose oldest-due age, queue depth, claim throughput, retry backlog and per-tenant wait time. For downtime recovery, use bounded concurrent processing with the existing claim fencing and provider-aware per-account pacing, rather than simply increasing the batch size while retaining a sequential loop. Add SQL tests for more than one batch of tied timestamps, deterministic selection, multiple tenants with uneven backlog, and recovery throughput assumptions.

**Evidence:** inspected migration `017_pinterest_schedule_worker.sql` and the later replacement definition in `060_pinterest_schedule_recovery_respects_safe_failure_journal.sql`; the current internal worker route in `backend/pinterest.js`; and `docs/pinterest/scheduler-setup.md`. The current function orders only by `scheduled_at`, clamps `p_limit` to 10, and checks overdue rows without an upper time bound. The setup guide specifies a cron call approximately once per minute with `{"limit":10}` and states that the cron is not yet configured in production. PostgreSQL's official `SELECT` documentation explains that `LIMIT` requires a unique ordering for a predictable subset and that `SKIP LOCKED` is intended for queue-like consumers: https://www.postgresql.org/docs/18/sql-select.html.

**Verification and scope:** static source, migration, and setup-document inspection only. No SQL fixture was executed, no production database or queue metrics were queried, and no production scheduler was contacted. No application code, migrations, or production state were changed by this finding.



### AUD-165-31 — Stale Pinterest claim recovery has no dedicated lookup index and is unbounded per worker call

**Finding confirmed:** the current `claim_due_pin_schedules()` function (migration 060) performs stale-claim reconciliation before claiming its bounded batch. It updates every row matching `status='publishing' AND updated_at < clock_timestamp() - interval '20 minutes'`; the update is not limited by `p_limit`. It also performs separate unbounded reconciliation updates for stale confirmed publications and journal outcomes.

The reviewed schema migrations create `pin_schedules_due_idx` on `(status, scheduled_at)` and `pin_schedules_retry_due_idx` on `(status, next_attempt_at, scheduled_at)`, both partial indexes restricted to `status='scheduled'`. Those indexes cannot directly serve the stale-recovery predicate for rows whose status is `publishing`. No dedicated partial index on `updated_at` for `status='publishing'` was found in the reviewed migrations.

**Impact:** as the schedule table grows, each worker invocation may need to examine a large portion of `pin_schedules` to find stale claims, and a single invocation can update/lock all stale rows rather than a bounded recovery batch. During a large outage this can create a long transaction, row-lock contention with workers and user actions, and delay the normal due-queue claim. This is a scaling risk inferred from the query predicates and available indexes; an actual sequential scan, latency, or production impact was not measured.

**Recommended remediation (not implemented):** evaluate a partial index such as `CREATE INDEX ... ON public.pin_schedules(updated_at) WHERE status='publishing'` (or a composite index if the final query plan warrants it). Consider processing stale claims in bounded `FOR UPDATE SKIP LOCKED` batches with deterministic ordering, preserving the existing claim-token fencing and journal reconciliation semantics. Do not weaken the 20-minute stale threshold or requeue ambiguous attempts merely to improve throughput. Capture `EXPLAIN (ANALYZE, BUFFERS)` on representative staging data and monitor recovery batch size, duration, rows examined, and lock waits before choosing the final index.

**Evidence:** migration `015_persistent_pin_schedule.sql` creates the scheduled-only due index; migration `034_pinterest_schedule_safe_retries.sql` adds a second scheduled-only retry index; migration `060_pinterest_schedule_recovery_respects_safe_failure_journal.sql` performs unbounded stale-recovery updates using `status='publishing'` and `updated_at < clock_timestamp() - interval '20 minutes'`. PostgreSQL documents that B-tree indexes can support filtering and ordered retrieval when their leading columns match query predicates, and that matching B-tree order can avoid an explicit sort for `ORDER BY ... LIMIT`: https://www.postgresql.org/docs/current/indexes-multicolumn.html and https://www.postgresql.org/docs/15/indexes-ordering.html.

**Verification and scope:** static inspection of migration definitions only. No production query plan, table size, index catalog, or lock metrics were accessed; no SQL tests were executed. No application code, migrations, or production state were changed by this finding.


### Follow-up verification — stale-claim fencing and late worker responses

**Concurrency review result:** the reviewed stale-recovery path does not blindly requeue a schedule once a publication attempt has been durably reserved. Migration 060 locks/reconciles the schedule row and classifies an old `publishing` row from its account-scoped attempt journal: a confirmed `published` attempt becomes `published`; a `failed/retry_safe=true` attempt may return to `scheduled`; a non-retry-safe failure becomes `failed`; any other existing attempt (including `processing` or `unknown`) becomes `unknown`; only a schedule with no attempt row is safely requeued. In all recovery transitions the claim token is cleared (also enforced by the trigger added in migration 060).

The reservation RPC `begin_scheduled_pinterest_publish()` checks `status='publishing'` and exact `claim_token` under a schedule row lock, after taking the account lock. Therefore, if recovery wins before an old worker has reserved its publication, the old worker cannot subsequently pass the stale token. If the reservation already exists, recovery preserves the attempt as `unknown` rather than making it eligible for a second create. The Pinterest HTTP client has a 10-second request timeout, substantially below the 20-minute stale threshold; even if a worker is paused after a remote create, the durable `processing` journal prevents automatic requeue and the completion RPC can reconcile the late confirmed success against the same pin/account/board.

The worker's catch-path schedule update is also conditional on both `status='publishing'` and the original `claim_token`, so a superseded worker cannot overwrite a recovered/reclaimed schedule. Completion does not take the claim token, intentionally: it records a confirmed remote side effect against the durable account-scoped attempt and reconciles active/unknown schedules. This is safe for the reviewed lifecycle because an ambiguous in-flight attempt is not automatically requeued; completion also validates the reserved board and rejects a conflicting remote publication identity.

**Existing regression coverage inspected (not executed):** `backend/test/pinterest-publication-concurrency.sh` explicitly races late completion against stale recovery and asserts convergence to one published remote identity; it also races completion against operator reconciliation. Static inspection only; this script was not run in this audit session, so no test-pass claim is made.

**Conclusion:** no additional duplicate-publication or stale-worker-overwrite finding was confirmed in this path. AUD-165-31 remains valid as a performance/scalability finding (unbounded recovery work and missing dedicated `publishing/updated_at` index), not a demonstrated fencing or duplicate-publication defect.


### Follow-up verification — publication uniqueness and reconciliation idempotency

**Concurrency review result:** the reviewed account-scoped schema enforces one publication attempt and one publication receipt per `(pin_id, pinterest_account_id)` through partial unique indexes (migration 033). It also enforces one active schedule per the same pair for statuses `scheduled`, `publishing`, `published`, and `unknown`. A pin may still be published to a different Pinterest account, as intended by the account-scoped model.

The current backend publishing path calls only `begin_pinterest_publish_v2` (or its schedule-claim wrapper), `fail_pinterest_publish_v2`, and `complete_pinterest_publish_v2`. The reservation RPC locks the Pinterest account row before creating or inspecting the unique attempt journal; the scheduled wrapper additionally validates the schedule's current claim token. Manual retry checks the account, schedule, absence of any attempt/publication journal, and absence of another active schedule before requeueing. Its row lock order is account -> schedule. The completion RPC uses account -> active/uncertain schedules in stable ID order -> attempt, then inserts the receipt with `ON CONFLICT DO NOTHING` and verifies that the stored remote pin ID and board exactly match the confirmed response. A conflicting remote identity is rejected rather than overwritten.

The operator reconciliation RPC is positive-only: it requires an aged `unknown` schedule and aged `unknown/processing` attempt, validates owner/account/board consistency and an evidence reference, inserts an append-only receipt keyed by unique `action_id`, and permits exact idempotent replay only for the same actor and payload. A unique constraint on `schedule_id` prevents a second operator receipt for the same schedule. It cannot mark a publication as absent or requeue it.

**Conclusion:** no new duplicate-attempt, duplicate-receipt, or conflicting-identity defect was confirmed in the reviewed current publishing and operator-reconciliation paths. This conclusion is based on static inspection of migrations 033, 035, 056, 057, 059, 061, 081, 082 and the current `backend/pinterest.js` / `backend/pinterestSchedule.js`; it is not a substitute for executing the database concurrency tests against the exact migration set. PostgreSQL row locks serialize conflicting writers/lockers on the same rows until transaction end, which is the basis for these guarantees (official PostgreSQL explicit-locking documentation).
