# AUD-190 — Безопасная смена Pinterest-доски у неудачного расписания

**Дата:** 2026-11-08  
**Область:** восстановление Pinterest schedule  
**Статус:** код и regression-сценарии добавлены в feature-ветку; миграция не применялась к production.

## Пользовательская проблема

Если Pinterest удалил доску или отозвал к ней доступ, расписание становилось failed. Пользователь видел объяснение, но для публикации того же пина на другой доске приходилось создавать новое расписание вручную. Это неудобно и повышает риск потери настроек.

## Что реализовано

### Backend
- Добавлен `POST /schedule/:id/change-board`.
- Новый board ID сначала проверяется через Pinterest API от имени того же подключённого аккаунта.
- Затем сервер вызывает атомарную RPC `change_failed_pin_schedule_board`.
- После изменения сервер возвращает обновлённое расписание, скрывая внутренний `last_error`.
- Endpoint доступен только на тарифах start/pro/agency, как и повтор публикации.

### Database migration 086
- Добавлена RPC `change_failed_pin_schedule_board(text, uuid, text)`.
- Блокировки выполняются в порядке account → schedule.
- Действие разрешено только для failed schedule с одной из двух известных ошибок проверки доски.
- Запрещено при любой публикационной попытке, которая не имеет `status='failed' AND retry_safe=true`, а также при существующей публикации.
- Запрещено при другом активном расписании или недоступном локальном пине.
- При успехе меняется только Pinterest board ID и состояние очереди; сохраняется исходный pin ID и его snapshot. Публикационная попытка не создаётся до запуска worker.
- RPC закрыта от public/anon/authenticated и доступна только service_role.

### Frontend
- В карточке failed schedule с причиной `board_unavailable` загружается список реальных Pinterest-досок именно привязанного аккаунта.
- Пользователь может выбрать другую доску и нажать «Сменить доску и возобновить».
- Сохраняются тот же пин, его изображение, текст, ссылка и настройки расписания.
- Другая доска не подставляется автоматически; выбор всегда явный.

## Регрессионные сценарии

В `backend/test/pinterest-account-publication.integration.sql` добавлены проверки:
1. Failed schedule без публикационной попытки успешно переводится на новую доску и возвращается в очередь с тем же pin ID.
2. Небезопасная failed attempt (`retry_safe=false`) блокирует смену доски и оставляет расписание failed на прежней доске.

## Проверки и ограничения

- После записи повторно проверено наличие endpoint, RPC, migration, frontend callback и UI.
- Полный backend test suite, TypeScript build и SQL integration script не запускались в этой среде.
- Миграция 086 добавлена в репозиторий, но не применялась к Supabase.
- Production, deploy и merge не затрагивались.

## Ожидаемое поведение

Если доска действительно недоступна, а журнал подтверждает, что Pinterest не получил публикацию, пользователь выбирает доступную доску — и существующее задание возвращается в очередь. Если результат прошлой отправки неоднозначен или есть публикация/небезопасная попытка, действие отклоняется, чтобы не создать дубликат.
