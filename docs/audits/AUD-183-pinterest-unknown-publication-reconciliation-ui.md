# AUD-183 — Интерфейс безопасной сверки неизвестной публикации Pinterest

**Дата:** 2026-11-08  
**Область:** административная очередь Pinterest, восстановление `unknown`  
**Статус:** исправление внесено в feature-ветку; production не затронут.

## Найденная проблема

Backend уже предоставлял защищённый маршрут `POST /admin/pinterest/reconcile-unknown-publication` и транзакционную SQL-процедуру, которая переводит запись в `published` только при наличии подтверждённого Pinterest Pin ID и Board ID. Однако компонент `AdminPinterestSchedules` показывал только подсказку «можно сверить» и оставался полностью read-only. У администратора не было интерфейса для запуска предусмотренной сервером безопасной сверки.

## Что изменено

- В `frontend/src/components/admin/AdminPinterestSchedules.tsx` добавлена форма для записей, которые backend предварительно пометил как пригодные к сверке.
- Форма просит Pinterest Pin ID, Board ID, источник подтверждения и номер обращения/записи. Известные локальные ID подставляются как начальные значения, но их можно проверить и исправить.
- Перед отправкой показывается отдельное подтверждение действия.
- Запрос отправляется только на существующий защищённый reconciliation endpoint; frontend не меняет статусы напрямую и не вызывает публикацию или retry.
- Для каждого действия генерируется UUID action_id. При сетевой ошибке форма сохраняет тот же action_id, чтобы повторная отправка того же действия оставалась идемпотентной на backend.
- После успешной сверки форма закрывается, а очередь перечитывается с сервера.
- Тексты интерфейса подчёркивают positive-only поведение: можно зафиксировать только уже найденный пин; отсутствие пина не доказывает, что публикация не состоялась, и не разблокирует повтор.

## Ожидаемое поведение

Если администратор действительно нашёл опубликованный пин в нужном Pinterest-аккаунте и на нужной доске, он сможет передать подтверждённые ID и ссылочный номер evidence. Сервер ещё раз проверит возраст и статус расписания, отсутствие активного claim, соответствие аккаунта/доски/пина, владельца и отсутствие конфликтующей публикации. Только после успешной транзакционной проверки PinPosy восстановит статус `published`.

Если администратор не может подтвердить существование пина, он не должен заполнять форму предположениями. Никакого автоматического повторного POST в Pinterest эта функция не запускает.

## Проверки

- Проверено наличие существующего backend маршрута и его защиты через authentication/admin middleware.
- Проверено соответствие полей формы контракту backend: `schedule_id`, `pinterest_pin_id`, `pinterest_board_id`, `evidence_type`, `evidence_reference`, `action_id`.
- Статически проверено, что JSON body сериализуется, action ID передаётся повторно при повторной отправке, форма показывается только при `actionable_reconciliation`, а подтверждение требуется до POST.
- Полный frontend TypeScript build и UI-тесты не запускались: в этой рабочей сессии нет локального checkout и установленных frontend dependencies.
- Backend/SQL интеграционные тесты не запускались; существующие backend-тесты reconciliation не изменялись.

## Безопасность и границы

- Изменён только frontend-компонент административной панели и этот audit log.
- SQL миграции не применялись, production не менялся, публикации и платежи не запускались.
- Это ручная фиксация положительного подтверждения, а не автоматический поиск пина в Pinterest API. Отрицательный результат поиска не считается безопасным основанием для повтора.
