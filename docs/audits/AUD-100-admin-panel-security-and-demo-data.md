# AUD-100 — административная панель: контроль доступа и демонстрационные данные

Дата: 2026-11-08  
Ветка: `feat/persisted-boards-api`

## Область проверки

Проверены серверная авторизация, получение административского признака, клиентское ограничение маршрута и источники данных административной панели.

## Результаты

### 1. Серверная авторизация административных маршрутов

В `backend/index.js` найдены следующие административные маршруты:

- `POST /admin/storage/reconcile-stale-uploads`
- `POST /admin/storage/quarantine-stale-uploads`
- `GET /admin/stats`
- `GET /admin/mail`
- `GET /admin/mail/:uid`
- `POST /admin/mail/reply`
- `GET /admin/subscriptions`
- `GET /admin/billing/email-outbox`
- `GET /admin/billing/webhook-exceptions`
- `GET /admin/billing/pending-orders`

Каждый найденный маршрут объявлен с обоими middleware: `requireAuth` и `requireAdmin`. Это защищает не только интерфейс, но и прямые HTTP-вызовы API.

### 2. Источник административских полномочий

- JWT содержит идентификатор пользователя и версию сессии, но не содержит доверенного клиентского флага администратора.
- `requireAuth` проверяет версию сессии в БД и устанавливает `req.userId`.
- `requireAdmin` повторно читает `users.is_admin` для этого ID из Supabase; при ошибке БД, отсутствии пользователя или отсутствии флага возвращает 403.
- `GET /me` возвращает `is_admin` только в рамках авторизованного запроса.
- `PATCH /me` обновляет только явно разрешённые поля профиля; `is_admin` в whitelist отсутствует.

Это правильная модель: клиентский флаг управляет только отображением, а сервер принимает решение по актуальному значению в БД.

### 3. Клиентский маршрут

`frontend/src/App.tsx` проверяет `isAdmin` из авторизованного профиля перед рендерингом `AdminPanel`. Само по себе это не является границей безопасности, но серверные административные маршруты независимо защищены.

### 4. Найденный риск: фиктивные финансовые и пользовательские сведения выглядели как реальные

`AdminPanel.tsx` использовал `ADMIN_USERS` и `ADMIN_TRANSACTIONS` из `adminMockData.ts`. Примеры включают вымышленные персональные данные, суммы платежей, себестоимость, налоговые расчёты и фискальные реквизиты. Без явного предупреждения оператор мог принять их за реальные сведения.

Выполнено:

- добавлено заметное предупреждение на всей странице админки;
- перечислено, какие вкладки и поля являются демонстрационными;
- указано не использовать эти значения для бухгалтерии, отчётности и связи с клиентами;
- отключена кнопка экспорта CSV, чтобы демонстрационные строки нельзя было выгрузить как налоговый отчёт.

Данные не удалялись, серверные платежи, почта и пользовательские записи не изменялись.

## Регрессионный тест

## Ограничения проверки

- Проверка выполнена статическим чтением исходников через GitHub API.
- Тесты, TypeScript build и frontend lint не запускались.
- Не выполнялись live-запросы к Supabase и попытки авторизации разными ролями.
- На предыдущем HEAD `5d95bb7` GitHub Actions показал failure для трёх PR workflows (Prodamus webhook tests, Persisted boards integration checks, Atomic payment fulfillment integration). Их логи недоступны через GitHub API в этой проверке; эти запуски не доказывают регрессию AUD-100. После добавления теста на HEAD `2a33670` новых PR workflow runs пока не появилось.
- Не проверялись реальные политики RLS/SQL grants и настройки Supabase service-role; это отдельный слой аудита.
- Не выполнялись операции reconcile/quarantine, отправка писем, платежи, возвраты, merge или deploy.
