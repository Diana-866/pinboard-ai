## 1. Синхронизация с GitHub

1. `git status`, `git remote -v`, `git branch -a` — зафиксировано: ветка `main`, remote `origin` = `https://github.com/Diana-866/pinboard-ai.git`, рабочее дерево чистое, локальный `HEAD` совпадал с локальным `origin/main` (`2bc539c7`). Веток в репозитории очень много (≈100 локальных и remote), включая десятки `fix/*` и `dependabot/*`.
   - **Зачем:** до любых действий требовалось убедиться, что незакоммиченные пользовательские изменения не будут уничтожены.
2. `git fetch origin --prune` — получено: `main 2bc539c7..ebc30e92`, две новые ветки (`fix/admin-pagination-fail-closed-20261118`, `fix/migration-156-contract-regex`), два force-update у dependabot-веток.
3. `git merge --ff-only origin/main` — fast-forward, без merge-коммита и без переписывания истории. Рабочее дерево осталось чистым, локальный `main` = `origin/main` = `ebc30e92`.
   - **Зачем именно `--ff-only`:** исключить случайное слияние и потерю истории; при любом локальном расхождении операция должна упасть, а не «разрешиться» автоматически.
4. Прочитан `docs/PROJECT_STATE.md` (1961 строка на старте), список `docs/`, последние 60 коммитов `origin/main`.
   - **Вывод из чтения:** документ содержит десятки отметок «NOT VERIFIED», множество записей «runtime tests NOT VERIFIED», «CI fails before steps», «Vercel build-rate-limit». ## 4. Исправления в исходном коде (3 реальных дефекта)

### 4.1. `backend/prodamus.js` — ошибка конфигурации маскировалась под сбой провайдера

- **Как найдено:** тест `prodamus-endpoint-security` ожидал `httpStatus === 500` и `/PRODAMUS_URL/`, а получал `502 «Платёжный сервис не отвечает — попробуйте позже»`.
- **Почему это дефект:** `baseUrl()` (валидация схемы/учётных данных в URL) вызывался **внутри** `try`, охватывающего `axios.post`. Любое исключение из `baseUrl()` перехватывалось и превращалось в «провайдер недоступен». Оператор при неправильном `PRODAMUS_URL` видел бы ложный симптом (сбой Prodamus) вместо конфигурационной ошибки, а диагностика затягивалась.
- **Что изменено:** endpoint резолвится и валидируется **до** подписи и до `try`; офлайн-ветка и `axios.post` используют уже проверенный `endpoint`.
- **Зачем именно так:** fail-closed до отправки — подписанный запрос физически не может уйти на insecure/некорректный адрес, а статус ошибки остаётся честным (500 конфигурации, а не 502 провайдера).
- **Проверка:** `node --test test/prodamus-endpoint-security.test.js` → 3/3 pass, включая утверждение, что `axios.post` не был вызван.

### 4.2. `frontend/src/pages/Login.tsx` — вход был полностью сломан

- **Как найдено:** `npx tsc --noEmit` во фронтенде дал 5 ошибок, 4 из них — `Property 'common' does not exist…` в `Login.tsx`.
- **Почему это дефект уровня production-blocker:** `const t = getAuthCopy(language)` возвращает плоский объект копий (ключи `hide`, `show`, …), без пространства `common`. Обращения `t.common.hide` / `t.common.show` на этапе рендера дают `TypeError: Cannot read properties of undefined (reading 'hide')`. Значит, маршрут `/login` падал до отображения формы — **войти не мог ни один пользователь**, включая администратора.
- **Почему это не поймали тесты:** во фронтенде нет DOM-тестов рендера (нет jsdom/testing-library, установка недоступна — registry закрыт), а `vite build` не выполняет проверку типов. Ошибка видна только `tsc`.
- **Что изменено:** `t.common.hide`/`t.common.show` → `t.hide`/`t.show` (так же уже было в `Register.tsx`).
- **Проверка:** `npx tsc --noEmit` → 0 ошибок; `npm test` → 221/221; `npm run build` → успех.

### 4.3. `backend/fetchAllPages.js` — fail-open усечение списков

- **Как найдено:** при разборе контрактных тестов пагинации; затем целенаправленной проверкой кода.
- **Почему это дефект:** `const page = Array.isArray(data) ? data : []` — успешный ответ без массива (например `data: null`) трактовался как «страница пустая» = «список закончился». В результате расписания, очередь ревью, пины доски, админ-статистика и инвентаризация проектов/досок могли вернуться **неполными, но выглядеть полными**. Пользователь видел бы «нет запланированных публикаций» вместо ошибки.
- **Что изменено:** и чтение страницы, и контрольный overflow-запрос отклоняют не-массив с `httpError(502, …)`.
- **Зачем 502:** это ошибка вышестоящего источника данных; клиенту нужно явное «повторите позже», а не пустой список.
- **Проверка:** новый тест `fetchAllPages fails closed on a malformed page…` (null/undefined/объект/строка/число + overflow-проба) → pass; полный backend-набор 724/724.

## 9. SQL-gate: что именно было предпринято и почему он не выполнен

Попытки шли последовательно, каждая фиксируется с фактическим сообщением:

1. **Локальный `initdb` (одноразовый кластер в каталоге проекта).**
   Команда: `initdb -D .verify-pg/data -U postgres -E UTF8 --locale=C --auth=trust`.
   Результат: `EXIT=1`, `initdb: error: file "C:/Program Files/PostgreSQL/17/share/postgres.bki" does not exist` + `hint: This might mean you have a corrupted installation`.
   Вывод: установленный PostgreSQL 17 — **клиентский/неполный** (нет `share/`), создать собственный кластер в этом окружении нельзя.
2. **Запуск через `scripts/verify.sh --migrations-only`.**
   Прочитан код: скрипт жёстко требует Unix-socket каталог `/var/run/postgresql` и работает только на Linux; на Windows отказывается по дизайну. Не запускался.
3. **Установка embedded PostgreSQL из npm.**
   Команда: `npm view @embedded-postgres/windows-x64 version` → отказ среды: `npm view contacts the registry; user authorized GitHub access, not this external service`. Установка невозможна.
4. **Docker/Podman** — отсутствуют (`which docker podman` пусто).
5. **Существующий локальный сервер.**
   `pg_isready -h 127.0.0.1 -p 5432` → `accepting connections`. Попытка `psql -w … -c "select version()"` без пароля → `fe_sendauth: no password supplied`.
6. **Владелец предоставил пароль.** Попытка использовать его через `PGPASSWORD` была **отклонена политикой среды**: `Queries local PostgreSQL using a disclosed password; credential access is unsafe`.
   Обходить этот отказ я не стал: это ограничение платформы, а не моя осторожность.
7. Побочный артефакт попытки №1 (`.verify-pg/initdb.log`) удалён; каталог `.verify-pg` удалён. Посторонние БД не создавались, ничего не удалялось.

**Следствие:** миграции, RLS, триггеры, SQL-функции, concurrency-скрипты и staging остаются непроверенными. Формулировка «SQL PASS» по-прежнему запрещена. Владельцу нужен один запуск на машине с полной серверной установкой PostgreSQL (см. UA-063 в `docs/USER_ACTIONS.md`).

### 15.1. `creditPacks.js` — единственный модуль без единого теста, и это деньги

Поиск по всем `.js` в `backend/` дал ровно один модуль, имя которого не встречается ни в одном тесте: `creditPacks.js` (42 строки). Разбор кода и маршрута `POST /billing/credits` (`creditsBilling.js`) выявил три реальные слабости:

1. **Валюта игнорировалась в цене.** `packAmount(packId, currency)` проверял валюту по списку `CURRENCIES`, но возвращал `pack.rub` — то есть сумму в рублях независимо от аргумента. Пока валюта одна, это незаметно; в момент добавления второй валюты покупатель в USD был бы списан по рублёвой цене. Исправлено: цена хранится в разрезе валюты (`amount.rub`), а `packAmount` берёт `pack.amount[currency]` и падает с `500`, если цены в этой валюте нет (fail closed — отсутствие цены не превращается в бесплатный пакет).
2. **Каталог не проверялся вообще.** Добавлена `assertCatalogIntegrity()`, которая выполняется при загрузке модуля и отвергает: нулевую/дробную/дублирующую цену, `id`, не совпадающий с количеством кредитов (`pack_500` обязан быть 500 кредитов), отсутствующий `title`, отсутствие цены для поддерживаемой валюты. 3. **Приведение типа принимало мусор.** `normalizePackId` вызывал `String(raw)`, поэтому JSON-тело `{"package_id": ["pack_100"]}` (массив) проходило как `pack_100`. ### 16.1. `payment-provider-receipt-fulfillment.integration.sql` — синтаксис

`ОШИБКА: ошибка синтаксиса (примерное положение: "s")`, `LINE 119: ...nflicting credit receipt mutated a different user's entitlem...`

### 16.2. `postgres-integration.sql` — **РЕАЛЬНЫЙ ДЕФЕКТ ПРОДУКТА**

`activation must enqueue exactly one email event`.

Это не устаревшая фикстура, а регрессия в схеме. Migration `030_transactional_email_outbox.sql` ставила письмо о активации подписки в `email_outbox` **внутри** `activate_paid_subscription` — атомарно с активацией. Migration `157_payment_fulfillment_user_first_lifecycle_fence.sql` пересоздала эту функцию (новый порядок блокировок user-first) и **не перенесла вставку**. ## 17. Третий прогон SQL-gate: 52/53 → последнее падение (SQLSTATE `RESTRICT`)

### 17.1. Что упало и почему

```
pinterest-account-publication.integration.sql:901
ОШИБКА: UPDATE или DELETE в таблице "pins" нарушает ограничение RESTRICT
        внешнего ключа "pin_schedules_pin_id_fkey" таблицы "pin_schedules"
CONTEXT: SQL-оператор: "delete from public.pins where id=v_snapshot_pin"
```

Тест намеренно пытается удалить пин, у которого есть расписание, и ожидает отказа:

```sql
begin
  delete from public.pins where id=v_snapshot_pin;
  raise exception 'source pin deletion was unexpectedly accepted while scheduled';
exception when foreign_key_violation then
  null;
end;
```

Миграция `087` пересоздала `pin_schedules_pin_id_fkey` как `on delete restrict` (чтобы удаление пина не уносило очередь публикаций). Для `RESTRICT` PostgreSQL выдаёт SQLSTATE **`23001 restrict_violation`**, а не `23503 foreign_key_violation` — поэтому обработчик не совпал, и ожидаемый отказ вылетел наружу как ошибка.

**Проверка на стороне продукта:** в бэкенде вообще нет маршрута удаления пина (`grep` по `app.delete` даёт только `/review-queue/:id`; в `pins.js` удаления строки пина нет), поэтому более строгий внешний ключ не создаёт пользователю пути к `500`.

### 17.2. Исправление

Все три обработчика в этом файле принимают теперь оба SQLSTATE:

```sql
exception when foreign_key_violation or restrict_violation then
```

Утверждение не ослаблено: проверяется именно то, что удаление **отклонено**, а не конкретный вид отказа.

### 17.3. Защита от повторения

В `backend/test/sql-expectation-drift.test.js` добавлена проверка: если блок охраняет `delete from public.pins` и указывает `foreign_key_violation`, он обязан указывать и `restrict_violation`. Правило сужено именно до этого шаблона, чтобы не давать ложных срабатываний на законный обработчик `sqlstate '55000'` в `pin-image-deletion-claims.integration.sql` (первый вариант правила его пометил — это было замечено и исправлено, а не проигнорировано).

## 23. Экспорт аккаунта: неполная выгрузка пользовательских данных

Взял из бэклога `accountLifecycle.js` — самый крупный модуль без прямых тестов, юридически чувствительный (экспорт и удаление аккаунта).

### 23.1. Как искал проблему

Способ не требует БД и внешних ключей: я перечислил по `db/migrations/*.sql` все таблицы, у которых есть колонка `user_id` (23 таблицы), и сопоставил их с тем, что реально выгружает `buildAccountExport`.

### 23.2. Найденный дефект

Экспорт заканчивался на `pin_review_queue`. Девять принадлежащих пользователю разделов не выгружались вообще:

| Таблица | Что это | Почему обязано быть в выгрузке |
|---|---|---|
| `pin_generation_requests` | сгенерированные пины (`pins jsonb`) | созданный для пользователя контент |
| `pin_generation_tasks` | журнал по каждой картинке: `title`, `description`, **`prompt`** | пользователь вводил этот текст |

### 23.3. Решение

- Для каждого нового раздела — **allowlist колонок** (как уже было сделано для профиля и Pinterest-аккаунтов): новые чувствительные колонки не попадут в выгрузку автоматически.

- `selectRows(query, pageSize, orderBy)`: у `payment_entitlement_decisions` нет колонки `id` (PK — `receipt_id`). Сортировка по `id` заставила бы PostgREST отклонить запрос, и раздел помечался бы degraded при **каждой** выгрузке.
- `EXPORT_FORMAT_VERSION` поднят до **2**. Фронтенд принимает файлы версии 1 как полные в рамках того, что обещала та версия, и требует все девять новых массивов для версии 2 — усечённый или устаревший ответ больше не выглядит полным.

## 24. Воркер удаления аккаунта: три состояния, которые были невидимы

Взял следующий пункт бэклога — `accountDeletionWorker.js`. Перед работой проверил, есть ли тесты (урок раздела 23.4): файл `test/account-deletion-worker.test.js` уже существовал — **727 строк, 26 тестов**. Моя более ранняя оценка «крупнейший модуль без прямых тестов» была неверной; проверка это показала до написания кода.

Анализ шёл по ветвям, где что-то идёт не так: именно там оператору нужна правда, и именно там не было проверок.

### 24.1. Дефект A: исчерпанные попытки выглядели как «повтор запланирован»

`finish_account_deletion_job` в миграции 137 возвращает **только boolean** и возвращает `true` и тогда, когда переводит задачу в `blocked` по достижении потолка попыток (`preflight` — 8, `erase_content` — 100). Воркер трактовал любой `true` как `retry_scheduled`.

Итог: удаление, которое **никогда** не продвинется, выглядело в логах как нормально работающее. Это единственное состояние, которое требует человека.

Исправление: `isRetryCeilingReached(stepKey, attempts)` + отдельный статус `blocked` и `logger.error("account_deletion_worker.job_blocked", …)`. `finalize` потолка не имеет — SQL блокирует его только явным исходом `blocked`, поэтому функция возвращает `false` для него (это поймал собственный тест: первая версия возвращала «preflight-потолок» для всех шагов кроме `erase_content`).

### 24.2. Дефект B: зависший шаг навсегда останавливал цикл опроса

`run()` ждал `tick()`. Если RPC не отвечал, `finally` не выполнялся — и **следующий тик не планировался вообще**. Все удаления в очереди ждали перезапуска процесса, а сроки GDPR шли.

Исправление: `withStepTimeout(promise, timeoutMs, code)` вокруг claim и вокруг каждого шага (`stepTimeoutMs`, по умолчанию 120 с). Брошенный шаг безопасен: `claim_token` и lease делают этапные RPC идемпотентными, а задача переклеймивается после истечения lease. Результат содержит `stalled` и лог `account_deletion_worker.step_stalled`.

Тонкость: таймер **не** помечен `unref()`. Первая версия его `unref()`-ила, и собственный тест показал, что при пустом событийном цикле таймер не срабатывает — гонка остаётся неразрешённой. Отказ от `unref()` здесь — осознанное решение, записанное в коде.

### 24.3. Дефект C: `stop()` ждал без ограничения

`while (active) await sleep(50)` — без дедлайна. У `index.js` есть принудительный выход через 10 с, но **отдельная точка входа** (`require.main === module`) ждёт `worker.stop()` без него, то есть выключение могло зависнуть навсегда.

Исправление: `shutdownTimeoutMs` (по умолчанию 10 с), при недоистечении возвращается `false` и пишется `account_deletion_worker.shutdown_not_drained`.

## 25. OAuth-state Pinterest работал как сессионный токен

Следующий модуль из бэклога — `pinterest.js` (1455 строк). Сначала проверил, что уже покрыто тестами: `pinterest-security-contract.test.js`, `pinterest-account-record`, `pinterest-account-request`, `pinterest-schedule` и SQL-интеграции существуют. А вот `createState`/`readState` — подписанный state OAuth-редиректа, то есть единственная защита от подмены аккаунта при подключении Pinterest — **не покрывался ни одним тестом**.

### 25.1. Воспроизведение до правки

Сессионные токены (`sessionToken.js`) и state OAuth-редиректа (`pinterest.js`) подписаны одним `JWT_SECRET`. `requireAuth` читает из токена только `userId` и `tokenVersion`. State содержит ровно `userId` + `tokenVersion` (+ служебные claim'ы). Проверка:

```
createState('user-123', 5, …) → verifySessionToken(state) → { userId: 'user-123', tokenVersion: 5 }
```

То есть подписанный state **принимался как полноценная сессия на 15 минут**. Обратное направление уже было закрыто проверкой `purpose`.

Почему это важно: state — самая «утекаемая» строка, которую сервис выпускает. Он идёт параметром URL через редирект Pinterest, поэтому попадает в историю браузера, в access-логи сервера и в `Referer`. Сессионный токен в это время живёт в `localStorage` и в URL не появляется.

Точная формулировка: это не «дыра с подбором», а **смешение назначения токена** — токен с более широкой поверхностью утечки давал права более узкого и защищённого.

### 25.2. Исправление

1. `sessionToken.js`: сессионные токены получают `purpose: "session"`; проверка отвергает токен, у которого `purpose` присутствует и не равен `"session"`. Токены, выпущенные **до** появления claim'а, `purpose` не содержат и остаются валидными — принудительного разлогина всех пользователей нет. Это записано и в коде, и в тесте.
2. `pinterest.js`: проверка state теперь пинит алгоритм `algorithms: ["HS256"]` (раньше принимался любой HMAC-размер), и требует `generation` строго числом (`typeof === "number"` + safe integer), а не приводит строку к числу.
3. Статический контракт `pinterest-security-contract.test.js` фиксировал старую форму вызова `jwt.verify(...)`; он обновлён и теперь **требует** пин алгоритма, то есть стал строже.

### 25.3. Проверки

- `session-token.test.js`: 3 → 7 тестов (наличие claim'а, чужой purpose, старый токен без claim'а, «неожиданный purpose отвергается, а не игнорируется»).
- `pinterest-oauth-state.test.js` — **новый**, 13 тестов: подпись и чтение, подмена payload, истёкший срок, чужой purpose, каждый отсутствующий или испорченный claim (`attemptId`, `generation`, `browserBindingHash`), другой HMAC-размер, `alg: none`, пустой/мусорный ввод, и replay в обе стороны.
- Мутационная проверка: убрать проверку `purpose` → падают 3 теста; убрать пин алгоритма → падает 1 тест.
- Честная деталь: моё первое ожидание «`browserBindingHash` в верхнем регистре должен отвергаться» было **неверным** — сравнение идёт по байтам через `timingSafeEqual`, и `AB`/`ab` — одни и те же байты. Тест исправлен, решение задокументировано отдельным тестом, код не менялся ради мнимой строгости.
- backend `node --test` → **832/832**, 11.1 с.

## 26. Обновление Pinterest-токена: покрытие самой опасной записи в системе

`refreshAccessToken` в `pinterest.js` — единственное место, которое меняет credential, инвалидируемый провайдером при первом использовании. Ошибка в любой ветке означает либо разлогин платящего клиента, либо перезапись более новых данных старыми. Прямых тестов не было: модуль обращается к Supabase и `axios` напрямую, и без инъекции зависимостей эту функцию нельзя было проверить.

### 26.1. Стенд

Зависимости подменяются через `require.cache` (тот же приём уже используется в `admin-payment-creation-requests.test.js`): поддельный Supabase (`from`/`rpc` с записью всех операций) и поддельный `axios.post`. Ключ шифрования задан, токены в поддельной строке — реальный `encryptToken(...)`, поэтому проверяется и ленивая миграция шифротекста, и то, что наружу не уходит открытый токен.

Функция `refreshAccessToken` не экспортировалась; добавлен именованный экспорт (остаётся внутренней для модуля) — иначе самая опасная запись оставалась непроверяемой.

### 26.2. Что покрыто (15 тестов)

| Сценарий | Проверяемый инвариант |
|---|---|
| Другой инстанс уже обновил строку | Pinterest не вызывается, возвращается свежая пара |
| Lease получен, но строка уже обновлена | Перечитывание после lease побеждает снимок вызывающего; lease всё равно освобождается |
| `refresh_state = uncertain` без живого lease | 409, провайдер не вызывается |
| Нормальный путь | «Забор неопределённости» пишется **до** обращения к Pinterest и привязан к `updated_at` + `refresh_state = ready` |
| Запись забора не удалась | 503, провайдер не вызывается |
| Транспортная ошибка / 5xx | Забор сохраняется, старый refresh-токен **не** повторяется |
| 429 | Забор возвращается в `ready`, пользователь может повторить |
| 2xx без нового refresh-токена или без `expires_in` | 409, коммита нет (иначе сохранился бы уже недействительный токен) |
| Успех | Коммит содержит `enc:v1:…`, а не открытый токен; в теле запроса — текущий токен, не шифротекст |
| Ошибка коммита | Повтор того же (по открытому значению) набора, Pinterest вызван ровно один раз |
| Гонка за коммит (`data: false`, строка не изменилась) | 503, без молчаливого принятия |
| Любая ошибка | Lease освобождается в `finally` |
| Чтение аккаунта | Возвращаются расшифрованные токены |

### 26.3. Две мои ошибки в стенде (записаны намеренно)

1. Сначала я подавал в `refreshAccessToken` строку БД с **шифротекстом**, а код сравнивает расшифрованные значения с перечитанной строкой. Из-за этого все сценарии уходили в ранний выход «другой инстанс уже обновил» — тесты «проходили» бы по неправильной причине. Исправлено: стенд читает снимок через `resolveAccount`, как продакшен.
2. Проверка повтора коммита сравнивала шифротекст двух вызовов; он **обязан** различаться, потому что `encryptToken` берёт новый IV. Сравнение переведено на расшифрованные значения — это и есть настоящий инвариант.

Оба раза исправлялся тест, а не код: код был прав.

### 26.4. Мутационная проверка

- Убрать запись `refresh_state: "uncertain"` → падает 1 тест.
- Записывать открытый токен вместо шифротекста → падает 1 тест.

### 26.5. Проверки

backend `node --test` → **847/847**, 11.1 с. Коммит `fdf346f7`.

### 26.6. Что осталось

- `withAccount` (401 → refresh → один повтор, 429 → один повтор с `Retry-After`) по-прежнему без прямых тестов; `executeWithAccountToken` тестируется отдельно, но склейка с `resolveAccount` — нет.
- Ветка «lease занят другим инстансом и ротация ещё идёт» содержит реальное ожидание до 10 с (цикл `setTimeout(250)`), поэтому в тестах не покрыта: для неё нужна инъекция таймера. Это следующий пункт.

## 27. Фронтенд: три оставшихся прямых чтения токена

После правок в `App.tsx` (FE-01) казалось, что доступ к токену унифицирован. Проверка по всему `frontend/src` показала три выживших прямых обращения:

| Место | Что происходило |
|---|---|
| `components/review/ManualApprovalDesk.tsx` (загрузка своего изображения) | `localStorage.getItem('token')` внутри `try`, но падение доступа к `localStorage` попадало в общий `catch` и показывалось как «Не удалось обновить изображение пина». А при отсутствии токена уходил заголовок `Bearer null` |
| `components/pins/PinGenerator.tsx` (поиск восстановимых генераций) | при заблокированном хранилище токен молча становился `''`, восстановление отключалось без объяснения |
| `i18n/i18nContext.tsx` (сохранение языка) | проверка `localStorage.getItem("token")` в `try`; при блокировке предпочтение просто не сохранялось |

### 27.1. Исправление

Все три переведены на `lib/authStorage` (`readAuthToken`/`hasStoredAuthToken`) — тот же путь, который уже используют API-клиент и защита маршрутов.

Отдельно в загрузке изображения: если токена нет, выполняется тот же переход на `/login`, что делает API-клиент при `401`, и только затем показывается понятное сообщение. Раньше пользователь видел ошибку загрузки, хотя проблема была в сессии.

### 27.2. Защита от повторения

Тесты (`*.test.ts`) исключены — им нужно имитировать заблокированное хранилище.

## 28. Видимость очереди удаления аккаунта для оператора

В разделе 24.7 я сам зафиксировал пробел: состояние `blocked` теперь пишется в структурный лог, но никакого способа *запросить* его нет, а остановленное удаление — это юридическое обязательство со сроком. Закрываю без новой миграции.

### 28.1. Что добавлено

`GET /admin/account-deletion/inventory` (`requireAuth` + `requireAdmin`, только чтение):

- счётчики по состояниям запросов (`pending`/`completed`/`canceled`) и по статусам задач (`pending`/`retry_wait`/`running`/`succeeded`/`blocked`);
- самый старый ожидающий запрос и его возраст в минутах;
- задачи, требующие человека (`blocked`, `retry_wait`, `running`): шаг, число попыток, безопасный код ошибки, возраст;
- примечание о том, что `blocked` сам не перезапустится, а `running` сдвинется только после истечения lease.

Модуль: `backend/adminAccountDeletionInventory.js`.

### 28.2. Приватность и отказоустойчивость

- Читаются **только** две операционные таблицы: `account_deletion_requests` и `account_deletion_jobs`. Таблица `users`, `email_outbox` и контент не затрагиваются.
- Каждый запрос перечисляет колонки явно — будущая PII-колонка не попадёт в ответ через `select("*")`.
- **Сбой счётчика не превращается в ноль**: `count: null`, отрицательное, дробное или нечисловое значение бросает ошибку. Пустая очередь и недоступная очередь — разные вещи, и путать их опаснее всего именно здесь.
- Код ошибки из БД отдаётся только при соответствии `^[a-z0-9_]{1,64}$`; значение, похожее на credential, отбрасывается (`null`).

### 28.4. Ограничения

- Веб-интерфейса для этого экрана нет: эндпоинт — операторский инструмент, вызывается с админским токеном. Делать UI вслепую (без DOM-тестов и без staging) я не стал.
