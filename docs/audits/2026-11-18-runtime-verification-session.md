## 4. Исправления в исходном коде (3 реальных дефекта)

### 4.1. `backend/prodamus.js` — ошибка конфигурации маскировалась под сбой провайдера

- **Как найдено:** тест `prodamus-endpoint-security` ожидал `httpStatus === 500` и `/PRODAMUS_URL/`, а получал `502 «Платёжный сервис не отвечает — попробуйте позже»`.
- **Почему это дефект:** `baseUrl()` (валидация схемы/учётных данных в URL) вызывался **внутри** `try`, охватывающего `axios.post`. Любое исключение из `baseUrl()` перехватывалось и превращалось в «провайдер недоступен». Оператор при неправильном `PRODAMUS_URL` видел бы ложный симптом (сбой Prodamus) вместо конфигурационной ошибки, а диагностика затягивалась.
- **Что изменено:** endpoint резолвится и валидируется **до** подписи и до `try`; офлайн-ветка и `axios.post` используют уже проверенный `endpoint`.
- **Зачем именно так:** fail-closed до отправки — подписанный запрос физически не может уйти на insecure/некорректный адрес, а статус ошибки остаётся честным (500 конфигурации, а не 502 провайдера).
- **Проверка:** `node --test test/prodamus-endpoint-security.test.js` → 3/3 pass, включая утверждение, что `axios.post` не был вызван.

### 4.2. `frontend/src/pages/Login.tsx` — вход был полностью сломан

- **Как найдено:** `npx tsc --noEmit` во фронтенде дал 5 ошибок, 4 из них — `Property 'common' does not exist…` в `Login.tsx`.
- **Почему это дефект уровня production-blocker:** `const t = getAuthCopy(language)` возвращает плоский объект копий (ключи `hide`, `show`, …), без пространства `common`. Обращения `t.common.hide` / `t.common.show` на этапе рендера дают `TypeError: Cannot read properties of undefined (reading 'hide')`. Значит, маршрут `/login` падал до отображения формы — **войти не мог ни один пользователь**, включая администратора.
- **Почему это не поймали тесты:** во фронтенде нет DOM-тестов рендера (нет jsdom/testing-library, установка недоступна — registry закрыт), а `vite build` не выполняет проверку типов. Ошибка видна только `tsc`.
- **Что изменено:** `t.common.hide`/`t.common.show` → `t.hide`/`t.show` (так же уже было в `Register.tsx`).
- **Проверка:** `npx tsc --noEmit` → 0 ошибок; `npm test` → 221/221; `npm run build` → успех.

### 4.3. `backend/fetchAllPages.js` — fail-open усечение списков

- **Как найдено:** при разборе контрактных тестов пагинации; затем целенаправленной проверкой кода.
- **Почему это дефект:** `const page = Array.isArray(data) ? data : []` — успешный ответ без массива (например `data: null`) трактовался как «страница пустая» = «список закончился». В результате расписания, очередь ревью, пины доски, админ-статистика и инвентаризация проектов/досок могли вернуться **неполными, но выглядеть полными**. Пользователь видел бы «нет запланированных публикаций» вместо ошибки.
- **Что изменено:** и чтение страницы, и контрольный overflow-запрос отклоняют не-массив с `httpError(502, …)`.
- **Зачем 502:** это ошибка вышестоящего источника данных; клиенту нужно явное «повторите позже», а не пустой список.
- **Проверка:** новый тест `fetchAllPages fails closed on a malformed page…` (null/undefined/объект/строка/число + overflow-проба) → pass; полный backend-набор 724/724.

## 9. SQL-gate: что именно было предпринято и почему он не выполнен

Попытки шли последовательно, каждая фиксируется с фактическим сообщением:

1. **Локальный `initdb` (одноразовый кластер в каталоге проекта).**
   Команда: `initdb -D .verify-pg/data -U postgres -E UTF8 --locale=C --auth=trust`.
   Результат: `EXIT=1`, `initdb: error: file "C:/Program Files/PostgreSQL/17/share/postgres.bki" does not exist` + `hint: This might mean you have a corrupted installation`.
   Вывод: установленный PostgreSQL 17 — **клиентский/неполный** (нет `share/`), создать собственный кластер в этом окружении нельзя.
2. **Запуск через `scripts/verify.sh --migrations-only`.**
   Прочитан код: скрипт жёстко требует Unix-socket каталог `/var/run/postgresql` и работает только на Linux; на Windows отказывается по дизайну. Не запускался.
3. **Установка embedded PostgreSQL из npm.**
   Команда: `npm view @embedded-postgres/windows-x64 version` → отказ среды: `npm view contacts the registry; user authorized GitHub access, not this external service`. Установка невозможна.
4. **Docker/Podman** — отсутствуют (`which docker podman` пусто).
5. **Существующий локальный сервер.**
   `pg_isready -h 127.0.0.1 -p 5432` → `accepting connections`. Попытка `psql -w … -c "select version()"` без пароля → `fe_sendauth: no password supplied`.
6. **Владелец предоставил пароль.** Попытка использовать его через `PGPASSWORD` была **отклонена политикой среды**: `Queries local PostgreSQL using a disclosed password; credential access is unsafe`.
   Обходить этот отказ я не стал: это ограничение платформы, а не моя осторожность.
7. Побочный артефакт попытки №1 (`.verify-pg/initdb.log`) удалён; каталог `.verify-pg` удалён. Посторонние БД не создавались, ничего не удалялось.

**Следствие:** миграции, RLS, триггеры, SQL-функции, concurrency-скрипты и staging остаются непроверенными. Формулировка «SQL PASS» по-прежнему запрещена. Владельцу нужен один запуск на машине с полной серверной установкой PostgreSQL (см. UA-063 в `docs/USER_ACTIONS.md`).

**Причина падения (найдена, не гипотеза):**


Поиск по всем `.js` в `backend/` дал ровно один модуль, имя которого не встречается ни в одном тесте: `creditPacks.js` (42 строки). Разбор кода и маршрута `POST /billing/credits` (`creditsBilling.js`) выявил три реальные слабости:

### 17.1. Что упало и почему

```
pinterest-account-publication.integration.sql:901
ОШИБКА: UPDATE или DELETE в таблице "pins" нарушает ограничение RESTRICT
        внешнего ключа "pin_schedules_pin_id_fkey" таблицы "pin_schedules"
CONTEXT: SQL-оператор: "delete from public.pins where id=v_snapshot_pin"
```

Тест намеренно пытается удалить пин, у которого есть расписание, и ожидает отказа:

```sql
begin
  delete from public.pins where id=v_snapshot_pin;
  raise exception 'source pin deletion was unexpectedly accepted while scheduled';
exception when foreign_key_violation then
  null;
end;
```

Миграция `087` пересоздала `pin_schedules_pin_id_fkey` как `on delete restrict` (чтобы удаление пина не уносило очередь публикаций). Для `RESTRICT` PostgreSQL выдаёт SQLSTATE **`23001 restrict_violation`**, а не `23503 foreign_key_violation` — поэтому обработчик не совпал, и ожидаемый отказ вылетел наружу как ошибка.

**Проверка на стороне продукта:** в бэкенде вообще нет маршрута удаления пина (`grep` по `app.delete` даёт только `/review-queue/:id`; в `pins.js` удаления строки пина нет), поэтому более строгий внешний ключ не создаёт пользователю пути к `500`.

### 17.2. Исправление

Все три обработчика в этом файле принимают теперь оба SQLSTATE:

```sql
exception when foreign_key_violation or restrict_violation then
```

Утверждение не ослаблено: проверяется именно то, что удаление **отклонено**, а не конкретный вид отказа.

### 17.3. Защита от повторения

В `backend/test/sql-expectation-drift.test.js` добавлена проверка: если блок охраняет `delete from public.pins` и указывает `foreign_key_violation`, он обязан указывать и `restrict_violation`. Правило сужено именно до этого шаблона, чтобы не давать ложных срабатываний на законный обработчик `sqlstate '55000'` в `pin-image-deletion-claims.integration.sql` (первый вариант правила его пометил — это было замечено и исправлено, а не проигнорировано).

Расшифровка mojibake-вывода: «Не удалось запустить Bash/Service/E_UNEXPECTED. Если эта ошибка была неожиданной, попробуйте найти сведения об ошибке или сообщить о новой проблеме по адресу https://github.com/microsoft/WSL/issues.»

То есть сценарии **вообще не запускались**: `Get-Command bash` в отдельной сессии PowerShell разрешился в `C:\Windows\System32\bash.exe` — это не POSIX-shell, а запускалка WSL. На машине без установленного дистрибутива WSL она лишь печатает эту ошибку и возвращает ненулевой код. Скрипт принимал кандидата по одному признаку «файл существует».

Отдельно: `Static SQL check OK (unknown files)` — счётчик файлов парсился из stdout дочернего процесса, а в реальном пайплайне строка-маркер не попадала в буфер.

### 19.2. Исправления

- `Find-Bash` теперь: (1) сначала пробует известные пути Git for Windows, включая встроенный git этого приложения; (2) **исключает** всё из `Windows\System32` и `Windows\SysWOW64`, откуда бы путь ни пришёл; (3) делает smoke-тест каждого кандидата (`bash -c "echo PINPOSY_POSIX_SHELL_OK"`, требуется код 0 и эта строка). Отклонённый кандидат печатается, а не используется молча.
- Счётчик SQL-файлов считается прямо в PowerShell (`Get-ChildItem -Recurse -Filter *.sql` по `db/` и `backend/test/`), без парсинга чужого stdout.

Проверено в текущем окружении: кандидат из `PATH` — встроенный git bash, smoke-тест проходит, значит фаза конкуренции здесь выполнима.

Причина: строка обрезана — у вызова `psql -c "... wait_event_type = 'Lock'"` отсутствовала закрывающая `")"`. Bash не мог распарсить файл, сценарий **никогда не запускался**. Три такие строки восстановлены. Проверено `bash -n` по всем 22 shell-скриптам репозитория — все парсятся.

## 24. Воркер удаления аккаунта: три состояния, которые были невидимы

Взял следующий пункт бэклога — `accountDeletionWorker.js`. Анализ шёл по ветвям, где что-то идёт не так: именно там оператору нужна правда, и именно там не было проверок.

### 24.1. Дефект A: исчерпанные попытки выглядели как «повтор запланирован»

`finish_account_deletion_job` в миграции 137 возвращает **только boolean** и возвращает `true` и тогда, когда переводит задачу в `blocked` по достижении потолка попыток (`preflight` — 8, `erase_content` — 100). Воркер трактовал любой `true` как `retry_scheduled`.

Итог: удаление, которое **никогда** не продвинется, выглядело в логах как нормально работающее. Это единственное состояние, которое требует человека.

Исправление: `isRetryCeilingReached(stepKey, attempts)` + отдельный статус `blocked` и `logger.error("account_deletion_worker.job_blocked", …)`. `finalize` потолка не имеет — SQL блокирует его только явным исходом `blocked`, поэтому функция возвращает `false` для него (это поймал собственный тест: первая версия возвращала «preflight-потолок» для всех шагов кроме `erase_content`).

### 24.2. Дефект B: зависший шаг навсегда останавливал цикл опроса

`run()` ждал `tick()`. Если RPC не отвечал, `finally` не выполнялся — и **следующий тик не планировался вообще**. Все удаления в очереди ждали перезапуска процесса, а сроки GDPR шли.

Исправление: `withStepTimeout(promise, timeoutMs, code)` вокруг claim и вокруг каждого шага (`stepTimeoutMs`, по умолчанию 120 с). Брошенный шаг безопасен: `claim_token` и lease делают этапные RPC идемпотентными, а задача переклеймивается после истечения lease. Результат содержит `stalled` и лог `account_deletion_worker.step_stalled`.

Тонкость: таймер **не** помечен `unref()`. Первая версия его `unref()`-ила, и собственный тест показал, что при пустом событийном цикле таймер не срабатывает — гонка остаётся неразрешённой. Отказ от `unref()` здесь — осознанное решение, записанное в коде.

### 24.3. Дефект C: `stop()` ждал без ограничения

`while (active) await sleep(50)` — без дедлайна. У `index.js` есть принудительный выход через 10 с, но **отдельная точка входа** (`require.main === module`) ждёт `worker.stop()` без него, то есть выключение могло зависнуть навсегда.

Исправление: `shutdownTimeoutMs` (по умолчанию 10 с), при недоистечении возвращается `false` и пишется `account_deletion_worker.shutdown_not_drained`.

## 25. OAuth-state Pinterest работал как сессионный токен

Следующий модуль из бэклога — `pinterest.js` (1455 строк). Сначала проверил, что уже покрыто тестами: `pinterest-security-contract.test.js`, `pinterest-account-record`, `pinterest-account-request`, `pinterest-schedule` и SQL-интеграции существуют. А вот `createState`/`readState` — подписанный state OAuth-редиректа, то есть единственная защита от подмены аккаунта при подключении Pinterest — **не покрывался ни одним тестом**.

### 25.1. Воспроизведение до правки

Сессионные токены (`sessionToken.js`) и state OAuth-редиректа (`pinterest.js`) подписаны одним `JWT_SECRET`. `requireAuth` читает из токена только `userId` и `tokenVersion`. State содержит ровно `userId` + `tokenVersion` (+ служебные claim'ы). Проверка:

```
createState('user-123', 5, …) → verifySessionToken(state) → { userId: 'user-123', tokenVersion: 5 }
```

То есть подписанный state **принимался как полноценная сессия на 15 минут**. Обратное направление уже было закрыто проверкой `purpose`.

Почему это важно: state — самая «утекаемая» строка, которую сервис выпускает. Он идёт параметром URL через редирект Pinterest, поэтому попадает в историю браузера, в access-логи сервера и в `Referer`. Сессионный токен в это время живёт в `localStorage` и в URL не появляется.

Точная формулировка: это не «дыра с подбором», а **смешение назначения токена** — токен с более широкой поверхностью утечки давал права более узкого и защищённого.

### 25.2. Исправление

1. `sessionToken.js`: сессионные токены получают `purpose: "session"`; проверка отвергает токен, у которого `purpose` присутствует и не равен `"session"`. Токены, выпущенные **до** появления claim'а, `purpose` не содержат и остаются валидными — принудительного разлогина всех пользователей нет. Это записано и в коде, и в тесте.
2. `pinterest.js`: проверка state теперь пинит алгоритм `algorithms: ["HS256"]` (раньше принимался любой HMAC-размер), и требует `generation` строго числом (`typeof === "number"` + safe integer), а не приводит строку к числу.
3. Статический контракт `pinterest-security-contract.test.js` фиксировал старую форму вызова `jwt.verify(...)`; он обновлён и теперь **требует** пин алгоритма, то есть стал строже.

## 26. Обновление Pinterest-токена: покрытие самой опасной записи в системе

`refreshAccessToken` в `pinterest.js` — единственное место, которое меняет credential, инвалидируемый провайдером при первом использовании. Ошибка в любой ветке означает либо разлогин платящего клиента, либо перезапись более новых данных старыми. ### 26.1. Стенд

Функция `refreshAccessToken` не экспортировалась; добавлен именованный экспорт (остаётся внутренней для модуля) — иначе самая опасная запись оставалась непроверяемой.

## 33. Дедлайн запроса и явный ответ 429

### 33.1. Что было не так

`frontend/src/lib/api.ts` знал ровно два исхода: ответ или общее «что-то пошло не так». Из этого следовали две реальные проблемы:

1. **Таймаута не было вообще.** `fetch` без сигнала не завершается сам, поэтому полуоткрытое соединение оставляло спиннер включённым до закрытия вкладки. Пользователь не мог ни повторить, ни понять, что произошло.
2. **429 не отличался от падения.** Глобальный лимитер (`API_RATE_LIMIT_MAX`) и лимитеры авторизации/ИИ отвечают 429 — ситуацию, которую лечит ожидание. Клиент показывал общее сообщение.

### 33.2. Решение

**Клиент** (`lib/api.ts`, новый `lib/apiResilience.ts`):

- каждый запрос идёт через `AbortController` с дедлайном 45 с; внешний `signal` вызывающего по-прежнему уважается (оба источника гасят один контроллер);
- собственный таймаут отличается от сетевой ошибки (`isAbortError`) и показывается отдельным сообщением;
- ожидание при 429 читается в порядке авторитетности: `retryAfterSeconds` из тела → `Retry-After` → `RateLimit-Reset`. Ожидание ≤ 3 с повторяется молча **один раз**; более долгое сообщается с реальным числом секунд на языке пользователя; при отсутствии пригодного значения — общее сообщение (выдумывать «подождите N секунд» хуже, чем не называть число);
- значение ограничено 300 с, чтобы враждебный заголовок не «пришпилил» клиент на час.

Новые сообщения `timeout` и `rateLimited` добавлены во все семь локалей `apiErrorMessages.ts`.

**Бэкенд** (`index.js`): все восемь лимитеров отвечают через один общий обработчик `rateLimitedHandler(message)` — сохраняет исходный текст, добавляет `code: "rate_limited"` и `retryAfterSeconds` в теле, равный значению заголовка.

### 33.3. Ошибка в моей собственной мотивировке

Сначала я исходил из того, что express-rate-limit 8 с `legacyHeaders: false` **не** отправляет `Retry-After`, и на этом строил обоснование. Проверил фактически (запрос к реальному приложению с дефолтным обработчиком): заголовок **есть**, `Retry-After: 60`. Настоящая причина, по которой клиент не мог отличить троттлинг от сбоя, другая: дефолтное тело — английская строка «Too many requests, please try again later.» без машинного поля, тогда как весь API отвечает по-русски. Мотивировка в коде, тесте и коммите исправлена; сама правка осталась, потому что код в теле и совпадение «тело = заголовок» — это то, что реально использует клиент.

Урок: проверять предпосылку измерением до того, как она попадёт в обоснование изменения.

### 33.4. Проверки

## 34. Дедлайн 45 с оборвал бы генерацию — таймаут на месте вызова

### 34.1. Найдено (в собственной правке предыдущего шага)

Дедлайн 45 с, добавленный на предыдущем шаге, был применён ко всем запросам одинаково. Проверка серверной стороны показала, что это регрессия для генерации изображений:

- `/boards/:id/pins/generate` генерирует до **10** картинок **последовательно** (`for (const task of tasks)` в `pins.js`);
- каждая задача у провайдера опрашивается до `maxPolls = 30` раз с интервалом 3 с (`gptunnel.js`), то есть до ~90 с на задачу плюс текстовый вызов (таймаут 30 с);
- итого законный запрос может идти **много минут**.

Клиентский обрыв на 45-й секунде дал бы худший из возможных исходов: пользователь видит ошибку, а сервер продолжает работу и **списывает кредиты**; результат при этом существует и восстановим по тому же `Idempotency-Key`, но UI об этом не знает.

### 34.2. Решение

`apiRequest` принимает `timeoutMs` в опциях запроса (`ApiRequestOptions = RequestInit & { timeoutMs?: number }`); по умолчанию действует прежний `REQUEST_TIMEOUT_MS = 45 000`, а место вызова генерации заявляет собственный бюджет `GENERATION_REQUEST_TIMEOUT_MS = 15 мин`. `timeoutMs` не передаётся в `fetch` (иначе браузер получил бы неизвестную опцию).

Бюджет заявлен **на месте вызова**, а не поднят глобально: обычный запрос должен падать быстро.

### 34.3. Проверки

Два новых теста в `apiResilience.test.ts`: бюджет генерации не меньше 10 минут и `PinGenerator` действительно его передаёт; `api.ts` умеет переопределять дедлайн и **не** пробрасывает `timeoutMs` в `fetch`.

Мутация: удалить `timeoutMs` из места вызова → тест падает.

frontend **259/259**, `tsc` — 0 ошибок, сборка проходит.

### 34.4. Настоящая архитектурная проблема (записана как риск, не исправлена)

Синхронная многоминутная генерация — риск сам по себе, независимо от клиента: любой обратный прокси перед бэкендом (Render, nginx) имеет idle-таймаут порядка 60–100 с и оборвёт ответ раньше, чем он будет готов. Тогда пользователь получит 502/504, а кредиты будут списаны. Это не проверяемо без staging (нужен реальный прокси), поэтому зафиксировано как открытый пункт с планом: перевести генерацию в асинхронную модель (202 + опрос статуса), для которой в проекте уже есть журнал запросов и восстановление по `Idempotency-Key`. Делать это «слепым» изменением без возможности прогнать живой сценарий — рискованно; нужен staging из UA-066.

## 35. Генерация, которая уже выполняется: ждать, а не падать

### 35.1. Сценарий

Пользователь перезагружает страницу во время генерации, дважды нажимает «Сгенерировать» или открывает вторую вкладку, которая повторяет сохранённый запрос. Бэкенд отвечает `409 generation_in_progress` — тот же ключ идемпотентности уже в работе. UI показывал это как ошибку, то есть перезагрузка выглядела как провал, хотя картинки продолжали генерироваться.

Сервер спроектирован так, что клиент должен **подождать и повторить тот же ключ**: готовый результат возвращается именно этому ключу, а ротация ключа запустила бы вторую генерацию и списала кредиты второй раз. `Retry-After: 5` сервер присылал с самого начала, но `ApiError` несёт JSON-тело, а не заголовки, поэтому клиент это значение не видел.

### 35.2. Решение

**Фронтенд** — `utils/generationPolling.ts`:

- `getGenerationInProgressWait(error)`: признаёт «ещё выполняется» только при `status === 409` **и** `data.code === "generation_in_progress"`; ожидание из тела, ограничено 300 с; при отсутствии поля — 5 с (сервер всегда рассчитан на опрос раз в несколько секунд, и потеря поля не должна превращать восстановимое состояние в ошибку);
- `runGenerationWithRecovery(request, {sleep, now, maxWaitMs, maxAttempts})`: повторяет **тот же** запрос, пока ошибка означает «ещё выполняется»; бюджет 10 мин и 60 повторов; всё, что не является сигналом «в процессе», пробрасывается немедленно — маскировать настоящую ошибку под медленную генерацию нельзя; при исчерпании бюджета выбрасывается последняя ошибка, чтобы пользователь увидел правду;
- `PinGenerator` фиксирует ключ один раз и передаёт его в каждый повтор; ротация ключа остаётся только для подтверждённой неудачи (`isDefinitiveGenerationFailure`).

**Бэкенд:** тело `409` для генерации и перегенерации, а также `202` для перегенерации теперь содержат `retryAfterSeconds`, совпадающий с заголовком (`5` и `10`). Тест сверяет тело и заголовок, чтобы клиент, читающий любое из двух, видел одно число.

### 35.3. Проверки

`frontend/src/utils/generationPolling.test.ts` — 9 тестов с внедрёнными часами и `sleep` (без реальных задержек): чтение и ограничение ожидания; `409` с другим кодом, `410` и `500` не считаются «в процессе»; повтор возвращает результат после двух отказов; настоящая ошибка пробрасывается **без** ожидания; бюджет 60 с при ожидании 30 с даёт ровно два ожидания и третью попытку; сервер с нулевым ожиданием не создаёт горячий цикл (срабатывает предел попыток); значения по умолчанию в разумных границах; компонент действительно использует цикл и не вращает ключ; тело и заголовок на бэкенде согласованы.

Мутация: убрать проверку кода → падает классификация (`409` с другим кодом был бы принят за «в процессе»).

## 36. Чужой lease обновления токена: непокрытая ветка стала покрытой

### 36.1. Почему это важнее остального

`refreshAccessToken` умеет три исхода при занятом lease: подождать, пока другой инстанс завершит ротацию, и взять его результат; продолжать ждать, если у `uncertain`-строки есть живой lease; попросить переподключение, если живого lease нет. Pinterest инвалидирует **оба** токена при каждом обновлении, поэтому звонок провайдеру со старой парой во время чужой ротации разлогинивает клиента. Это единственное место, которое решает, можно ли вообще обращаться к провайдеру, — и оно было непокрыто: ожидание использовало реальные `Date.now()` и `setTimeout(250)` до 10 секунд.

### 36.2. Сделано

- `refreshAccessToken(account, timing = {})` принимает инъекцию `now`, `sleep`, `maxWaitMs`, `pollMs`; продакшн-значения по умолчанию не изменились (10 000 мс, 250 мс). Границы 10/250 вынесены в константы `REFRESH_CONCURRENCY_WAIT_MS` и `REFRESH_CONCURRENCY_POLL_MS`.
- Проверка живого lease теперь использует **тот же** внедрённый `now`, а не второй `Date.now()`. Это не косметика: с двумя источниками времени ожидание и решение о lease расходятся, и ветка становится недетерминированной — тест на живом lease падал именно из-за этого (мои «часы» были в прошлом относительно реального времени, и живой lease выглядел истёкшим).

### 36.3. Проверки

Шесть тестов на «плёночных» часах и двойнике Supabase, который умеет ломать запрос lease:

1. ротация другого инстанса подхватывается **без** обращения к Pinterest (0 вызовов провайдера);
2. живой lease у `uncertain`-строки дожидается конца бюджета и даёт 503 «уже выполняется»;
3. `uncertain` без живого lease сразу даёт 409 «Подключите аккаунт заново»;
4. нечитаемое состояние lease даёт 503, а не догадку;
5. аккаунт, отключённый во время ожидания, останавливает ожидание немедленно (409);
6. уже ротированная строка используется после одного опроса, без полного бюджета.

Мутации (обе проверены на факт применения — прошлый опыт показал, что «мутация, которая не применилась» выглядит как прошедший тест): пропуск ветки ожидания ломает 4 теста, снятие проверки живого lease — 2.

backend **883/883**. Коммит `053ca218`. Записи: раздел 36, реестр (строки 104–107).

## 39. 402 «недостаточно кредитов»: один код и локализация в одном месте

### 39.1. Почему это важный сценарий

402 — самая частая ошибка платящего клиента: баланс не покрывает операцию или фактическая стоимость оказалась выше резерва. В `index.js` таких мест было **девять**, каждое со своим русским текстом; два использовали собственное имя кода (`generation_insufficient_credits`), остальные не имели машинного поля вообще. Следствие: шесть из семи языков интерфейса показывали русский текст, и ни один вариант не подсказывал единственное полезное действие — пополнить баланс.

### 39.2. Сделано

**Бэкенд:** один помощник `insufficientCreditsError(message)`; все девять мест переведены на него, поэтому каждый 402 несёт `code: "insufficient_credits"`. Подробный текст сохранён (логи и поддержка), прежние самодельные имена кодов убраны, чтобы у клиента было одно значение для маппинга.

**Фронтенд:** `appErrorCopy` получил ключ `insufficientCredits` на семь языков; слой запросов локализует **известные коды в одном месте** (`getLocalizedApiError`), а не в двадцати экранах: известный код → локализованное сообщение, неизвестный → серверный текст (придумывать смысл для непонятной ошибки нельзя). `data.code` по-прежнему доходит до вызывающего кода — экраны на него ветвятся.

### 39.3. Проверки

## 41. 422: гибрид — коды для исправимых ошибок, серверный текст для внутренних

### 41.1. Решение, которое нужно было принять до работы

В разделе 40 осталось: 422 — самый большой класс (28 мест), но сообщения специфичны для каждого правила. Код на каждое правило означал бы ~200 переводов; общие коды («некорректные данные») уничтожили бы смысл сообщения. Принят **гибрид**:

- **ошибка, которую клиент может вызвать и исправить** → код + перевод;
- **нарушение внутреннего контракта** (некорректный `Idempotency-Key`, неизвестный статус, «нечего обновлять», отсутствующий `project_id`) → остаётся серверный текст: человек всё равно ничего не может с этим сделать, а перевод занял бы семь строк без пользы.

### 41.2. Сделано

Девять кодов: `board_name_required`, `invalid_schedule_time`, `schedule_too_far`, `invalid_timezone`, `project_url_required`, `project_url_invalid`, `pin_image_missing`, `board_selection_required`, `image_upload_required` — через помощник `validationError(code, message)`. Русский текст сохранён.

Тексты построены так, чтобы говорить, **что сделать** («добавьте адрес сайта в настройках проекта», «выберите доску перед планированием», «сначала сгенерируйте изображение»), а не только констатировать, что что-то не так.

### 41.3. Проверки

`frontend/src/lib/validationErrorLocalization.test.ts` — 5 тестов:

1. все девять кодов переведены на все семь языков;
2. сообщения различаются и называют объект исправления (включая проверку китайских строк с вырезанными техническими латинскими словами: `Pinterest`, `HTTP`, `PNG`, `MB` и т.п.);
3. код валидации переводится **только** при статусе 422, а неизвестный код сохраняет серверный текст;
4. множество кодов, которые отдаёт бэкенд, и множество в таблице маппинга на клиенте **совпадают** — таблица читается из исходника, поэтому «код с переводом, который никто не отдаёт» тоже падает;

Мутации (обе проверены на применение): снять код с одного правила → два теста падают; добавить в маппинг код, которого бэкенд не отдаёт → падает сравнение множеств.

## 43. Почта: таймауты SMTP и утечка конфигурации

### 43.1. Найдено

Транзакционная почта — критический путь: письмо подтверждения, сброс пароля, уведомление об активации тарифа. Проверка `mail.js` дала два дефекта:

1. **Транспорт создавался без таймаутов.** Действуют значения nodemailer по умолчанию: `connectionTimeout` 2 мин, `greetingTimeout` 30 с, `socketTimeout` до 10 мин. Зависший SMTP держал бы запрос регистрации открытым намного дольше, чем клиент готов ждать (у клиента дедлайн 45 с), занимая соединение и воркер на инстансе, где их мало. То же самое было у отправки ответов поддержки.
2. **Сообщения об ошибке называли переменные окружения**: «задайте MAIL_SMTP_HOST, MAIL_SMTP_USER и MAIL_SMTP_PASS на сервере» (и аналогично для IMAP/reply). Этот текст доходит до того, кто вызвал путь, включая анонимного посетителя на регистрации, то есть конфигурация развёртывания раскрывалась в теле ответа API.

### 43.2. Сделано

- `mailTransportTimeouts()` — одна политика для всех транспортов: соединение 10 с, приветствие 10 с, сокет 30 с. `buildTransactionalTransportOptions()` и `buildReplyTransportOptions(config)` собирают конфигурацию (решение о TLS по-прежнему привязано к порту: 465 → `secure`, 587 → `requireTLS`).
- Все сообщения обезличены («Отправка писем временно недоступна. Попробуйте позже.», «Почтовый ящик временно недоступен…», «Ответы поддержки временно недоступны…»), причина уходит в лог (`mail.event_003/004/005`).

### 43.3. Проверки

`backend/test/mail-transport.test.js` — 6 тестов: таймауты присутствуют и ограничены (и сокет живёт дольше рукопожатия), TLS следует за портом включая значение 465 по умолчанию, ненастроенное развёртывание не называет переменные и при этом не падает для вызывающих с `needThrow: false`, а каждый `createTransport` получает **проверенный построитель**, а не инлайновый объект (иначе таймауты снова потеряются).

Мутации (обе проверены на применение): убрать таймауты → падает тест транспорта; вернуть `MAIL_SMTP_HOST` в сообщение → падают два теста.

backend **889/889**. Коммит `4e48296e`. Записи: раздел 43, реестр (строки 126–128).

### 43.4. Что осталось

У SMTP-отправки нет **пулинга соединений**: каждый конверт — новый TLS-хендшейк. При массовых рассылках (например, после активации тарифа для всех) это дорого; нужен `pool: true` с ограничением, но это меняет поведение и требует проверки на реальном SMTP (staging, UA-066). Отправка писем из очереди (миграция 162) уже отдельная сущность, поэтому этот шаг не блокирует регистрацию.
