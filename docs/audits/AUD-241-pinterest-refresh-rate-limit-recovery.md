# AUD-241 — безопасное восстановление после Pinterest refresh rate limit

Дата: 2026-11-09

## Проблема
`refreshAccessToken` предварительно переводит аккаунт в `refresh_state='uncertain'`, чтобы никогда не повторять старый refresh token после неоднозначного результата. Однако ранее любой полученный HTTP-ответ вне 2xx, включая явный `429 Too Many Requests`, оставлял аккаунт в uncertain и возвращал ошибку с требованием повторно подключить Pinterest.

Для явного 429 это чрезмерно: провайдер явно отклонил попытку из-за ограничения частоты. Пользователь не должен проходить OAuth заново из-за временного rate limit.

## Исправление
- Добавлен `isExplicitRefreshRateLimit(status)`: только HTTP 429 классифицируется как явный rate-limit отказ.
- При 429 backend снимает uncertainty fence только условным обновлением той же строки аккаунта: совпадают account ID, user ID, `updated_at` маркера и `refresh_state='uncertain'`.
- Если условное обновление не подтвердилось, backend не ослабляет защиту и возвращает 503.
- После успешного снятия fence возвращается 503 с сообщением подождать и повторить действие позже. OAuth повторно не запускается автоматически.
- Таймауты, сетевые ошибки, 5xx, неполные 2xx-ответы и прочие статусы сохраняют прежнее консервативное поведение: uncertainty fence остаётся, старый refresh token не переиспользуется, требуется повторная OAuth-авторизация.
- Условие `updated_at` защищает от гонки: поздняя обработка 429 не может сбросить состояние после reconnect или более нового изменения аккаунта.

## Регрессии
- Unit tests: HTTP 429 распознаётся как явное ограничение; 4xx (кроме 429), 5xx, timeout-like статусы и отсутствие статуса не классифицируются как безопасный retry.
- PostgreSQL integration SQL: проверяется снятие точного uncertainty fence после 429 и защита от stale cleanup после reconnect.
- Существующий workflow уже запускает `backend/test/pinterest-refresh-disconnect-fencing.integration.sql`; новая SQL-регрессия включена в этот файл, отдельный шаг workflow не нужен.
