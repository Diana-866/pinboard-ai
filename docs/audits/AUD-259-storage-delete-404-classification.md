# AUD-259 — Строгая классификация Storage 404 при удалении

## Найденный дефект
Удаление изображения считалось успешным при любом ответе Storage со статусом 404. Но HTTP 404 может означать отсутствие не только конкретного объекта, но и бакета/endpoint. В таком случае lifecycle ошибочно переводил путь в `deleted`, хотя Storage удаление не подтвердил.

## Исправление
- Добавлена `isStorageObjectNotFound(error)`.
- Успешным отсутствием объекта считается только статус 404 вместе с известным object-specific кодом (`not_found`, `object_not_found`, `no_such_key`) и сообщением, явно указывающим на отсутствующий object/key.
- Любой общий или неясный 404 проходит как определённый отказ: lifecycle фиксирует `delete_failed` через token-checked finalization и возвращает ошибку вызывающему коду.
- 5xx и transport errors по-прежнему оставляют deletion claim fenced; автоматическое снятие блокировки не выполняется.

## Регресс-тесты
- object-specific 404 считается подтверждённым отсутствием объекта;
- `Bucket not found` и общий `Not found` не считаются подтверждением;
- generic 404 фиксируется как неуспешное удаление, не как `deleted`.

## Проверка и ограничения
- Изменения записаны в `feat/persisted-boards-api`, файлы перечитаны из GitHub.
- Node/PostgreSQL тесты локально не запускались; GitHub Actions на текущем HEAD возвращает failure без доступных шагов/логов, поэтому результат тестов не подтверждён.
- Production DB/Storage, deployment и merge не затрагивались.
