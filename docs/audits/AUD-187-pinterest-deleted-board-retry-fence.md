# AUD-187 — Блокировка повторов при удалённой Pinterest-доске

**Дата:** 2026-11-08  
**Область:** предварительная проверка Pinterest-доски и политика retry фонового worker  
**Статус:** исправление и regression test добавлены в feature-ветку; production не затронут.

## Найденный дефект

Worker использует журнал публикации, чтобы разрешать повтор только после явно безопасного отказа. Но если в журнале уже была старая запись `failed / retry_safe=true`, а доска Pinterest позже удалялась или становилась недоступной, предварительный `GET /boards/{board_id}` возвращал 403/404. Проверка доски завершалась до новой резервации публикации, однако worker всё равно мог принять решение о retry по старой безопасной записи.

Это приводило к повторным бесполезным обращениям к недоступной доске и могло снова возвращать задание в очередь.

## Исправление

- `verifyPinterestBoard` помечает подтверждённые ошибки предварительной проверки и несовпадение ID как `retryable=false`.
- `canRetryScheduleFailure` сначала учитывает текущий терминальный отказ, а уже затем старую запись журнала.
- Старая запись `retry_safe=true` больше не может переопределить текущий отказ проверки доски.
- Неопределённые состояния `unknown/processing` остаются заблокированными.
- Временные ошибки без терминального признака и явно безопасные journal failures сохраняют прежнюю retry-политику.

## Проверка

Добавлен regression test: старый `failed / retry_safe=true` вместе с текущей терминальной ошибкой проверки доски не разрешает повтор.

Изолированно выполнен Node.js test-runner для политики retry: **3 теста пройдены** (терминальный отказ доски, сохранение допустимого retry для временной ошибки, блокировка unknown). Полный `backend/test/pinterest-schedule.test.js`, backend suite, SQL integration и frontend build в этой сессии не запускались.

## Безопасность и границы

- Исправление не меняет сохранённый board ID и не перенаправляет публикацию на другую доску.
- Пользователю потребуется выбрать/привязать доступную доску и явно восстановить задание предусмотренным UI-процессом.
- POST `/pins` и правила неопределённого результата не ослаблялись.
- Production, Supabase и расписания реальных пользователей не изменялись; миграции и деплой не выполнялись.
