# AUD-184 — Корректная обработка конкурентной сверки Pinterest

**Дата:** 2026-11-08  
**Область:** backend HTTP-обработка ошибок операционной сверки неизвестных публикаций  
**Статус:** исправление и тесты внесены в feature-ветку; production не затронут.

## Проблема

SQL-функция `admin_reconcile_pinterest_unknown_publication` защищает журнал от повторной фиксации одной публикации и от повторного использования action ID с другим содержимым. При двух параллельных действиях база закономерно отклоняет проигравший запрос ограничением уникальности (SQLSTATE `23505`). Конкурентное изменение также может дать `40001`.

Backend ранее преобразовывал такие ошибки в общий HTTP 500. Это неверно описывало ситуацию: запись могла уже быть успешно восстановлена первым запросом, а второй запрос просто столкнулся с конфликтом. Общая ошибка также затрудняла оператору понимание, что нужно обновить список, а не повторять действие с новыми данными.

## Исправление

В `backend/adminPinterestReconciliation.js`:

- SQLSTATE `23505` (уникальный конфликт) и `40001` (конкурентное изменение) теперь отображаются в HTTP 409.
- Текст ответа нейтрально сообщает, что публикация уже сверяется либо данные действия отличаются от ранее принятого запроса.
- Конфликт повторного action ID с другим payload также отображается как 409.
- Внутреннее сообщение базы данных по-прежнему не раскрывается клиенту.

В `backend/test/admin-pinterest-reconciliation.test.js` добавлены проверки:
- повторная фиксация одного schedule через уникальное ограничение;
- повтор action ID с другим payload;
- конфликт сериализации при конкурентном изменении.

## Результат для пользователя

Если два оператора одновременно подтверждают один и тот же найденный пин, база не создаст две записи. Запрос, который проиграл гонку, получит понятный конфликт вместо ложного сообщения о внутренней поломке сервера. Оператор сможет обновить очередь и увидеть фактическое состояние.

Важно: HTTP 409 не означает, что повторная публикация безопасна. Этот маршрут остаётся только для подтверждения уже существующего пина; он не отправляет новый пин в Pinterest и не доказывает отсутствие публикации.

## Проверки и ограничения

- Изучены SQL-ограничения уникальности и идемпотентный replay в миграции `082_pinterest_operator_publication_reconciliation.sql`.
- Добавлены три узких backend-теста для SQLSTATE `23505`, `40001` и несовпадающего replay payload.
- Проверена статическая согласованность веток обработки ошибок и ожидаемых HTTP 409.
- Полный backend test suite и интеграционные тесты PostgreSQL не запускались в этой сессии.
- Миграции не применялись, production не менялся.
