# База данных PinPosy

База данных — PostgreSQL (ранее использовался Supabase). В репозитории находятся две исторические схемы. Для текущего backend актуальна только новая цепочка ниже.

## Важно: не смешивать цепочки миграций

- `001_baseline.sql` — актуальный полный baseline для текущего backend.
- `001_base_schema.sql` и миграции `002`–`008` — прежняя историческая цепочка. Она сохранена для справки и не должна запускаться вместе с новой цепочкой.
- `009_hardening.sql` меняет типы `user_id`, удаляет некорректные и осиротевшие записи, добавляет внешние ключи. Перед его запуском обязателен аудит данных и резервная копия.
- `010_atomic_credit_ledger.sql` и `011_atomic_subscription_activation.sql` добавляют RPC-функции, которые уже вызываются текущим backend.

## Текущая последовательность для новой тестовой базы

Применять строго по порядку на отдельной пустой тестовой БД:

1. `001_baseline.sql` — полная базовая схема (10 таблиц, индексы, RLS и базовая функция).
2. `009_hardening.sql` — нормализация типов user_id, внешние ключи и дополнительные ограничения.
3. `010_atomic_credit_ledger.sql` — атомарное изменение баланса и журналирование покупок кредитов.
4. `011_atomic_subscription_activation.sql` — атомарная активация подписки.

После каждого шага проверять отсутствие SQL-ошибок. Затем выполнить интеграционные SQL-проверки из `backend/test/postgres-integration.sql` в тестовом окружении.

## Запрещённый сценарий

Не выполнять последовательность `001_base_schema.sql` → `002` → … → `008` → `009` → `010` → `011` как одну цепочку. Старая `001_base_schema.sql` и новая `001_baseline.sql` — альтернативные исходные схемы.

Не запускать миграции на production до:
- определения фактической схемы и версии PostgreSQL;
- создания и проверки восстановления резервной копии;
- подсчёта строк с некорректными/осиротевшими user_id, которые `009` может удалить;
- сверки типов колонок и существующих ограничений с новой схемой;
- отдельного плана применения и отката.

## Что делает новая цепочка

| Файл | Назначение |
|---|---|
| `001_baseline.sql` | Полная исходная схема: users, projects, boards, pins, credit_transactions, auth_tokens, subscriptions, credit_purchases, pinterest_accounts, pinterest_publications; индексы, RLS и базовая RPC-функция. |
| `009_hardening.sql` | Приводит user_id зависимых таблиц к UUID, удаляет некорректные и осиротевшие строки, добавляет FK, триггер updated_at, проверки статусов и индексы. |
| `010_atomic_credit_ledger.sql` | Создаёт атомарную RPC-операцию изменения баланса и журналирования, а также идемпотентное начисление оплаченной покупки. |
| `011_atomic_subscription_activation.sql` | Создаёт атомарную и идемпотентную активацию оплаченной подписки. |

## Проверки совместимости backend

Текущий backend вызывает следующие функции PostgreSQL:
- `adjust_credits_balance_and_log(text, integer, text, text)` — `backend/credits.js`.
- `credit_paid_purchase(uuid, timestamptz, text)` — `backend/creditsBilling.js`.
- `activate_paid_subscription(uuid, timestamptz)` — `backend/billing.js`.

Наличие только старой `adjust_credits_balance(text, integer)` из исторической схемы недостаточно для текущего backend.

Backend использует `SUPABASE_SERVICE_ROLE_KEY` и собственные JWT PinPosy; это не Supabase Auth. RLS-политики не заменяют серверную авторизацию. Прямой клиентский доступ к таблицам не следует открывать.

## Важные настройки вне SQL

- `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` — серверные переменные окружения. Service-role ключ нельзя публиковать во frontend.
- Storage bucket `pin-images` создаётся backend-модулем при необходимости; сейчас bucket публичный, поэтому URL изображения доступен по ссылке.
- Резервное копирование, PITR, сетевой доступ, роли, лимиты и мониторинг не создаются этими SQL-файлами и требуют отдельной настройки платформы.

## Текущий статус проверки

- Ветка содержит PostgreSQL integration workflow, который поднимает временный PostgreSQL 16, создаёт совместимые роли Supabase и применяет `001_baseline.sql`, `009`, `010`, `011` с SQL-проверками атомарных операций.
- Успешный CI на временной базе подтверждает работоспособность цепочки в чистом тестовом окружении, но не доказывает совместимость с текущей production-базой.
- Состояние production-схемы и содержимое production-данных в рамках этого документа не проверялись.

## Откат

Автоматических down-миграций нет. Не удалять таблицы и не выполнять DROP на production ради отката. Для production нужен проверенный backup/PITR либо отдельные согласованные обратные SQL-операции после анализа фактического состояния.
