# PinPosy — аудит состояния и план доведения до запуска

**Дата:** 2026-11-21 (MSK)
**Кто:** Spark, команда Дианы Банновой
**Что проверено:** архив `PIN.zip` (рабочее дерево + git-история, HEAD `5486a264`), живой сервис `pinposy.com` / `pinboard-ai-backend.onrender.com`, локальный прогон тестов, миграций и сборки.
**Чем проверено:** Node.js 22.23, PostgreSQL 16.15 (установлен в рабочей среде), frontend-зависимости переустановлены из npm.

## 1. Главное в трёх строках

1. **Сервис сейчас не обслуживает пользователей:** вход и регистрация на живом бэкенде отвечают `503 «Внутренняя ошибка сервера»`, проверка готовности `/ready` — `503 database_unavailable`. Сайт открывается, но внутрь войти нельзя.
2. **Код при этом в рабочем состоянии:** 1438/1438 backend-тестов, 426/426 frontend-тестов, TypeScript, production-сборка и полная цепочка миграций `001 + 010–166` на чистой PostgreSQL проходят. 51/51 SQL-интеграционных тестов — тоже.
3. **Причина отказа — конфигурация на Render, а не база и не код:** та же база Supabase с ключом из проектного `.env` извне отвечает за 0,7 с и отдаёт таблицу `users`. Значит, на Render неверны переменные окружения (или сеть сервиса), и это первое, что нужно поправить.

## 3. Дефекты, найденные и исправленные сегодня

### D-1. Проверка репозитория `scripts/verify.sh` и `scripts/verify.ps1` не могла пройти никогда
Скрипты требовали непрерывную цепочку миграций `010–165` (152 файла), а в репозитории уже `010–166` (157 файлов). Оба скрипта отказывались запускать replay и завершались ошибкой — то есть «одна команда, отвечающая на вопрос, работает ли репозиторий» была сломана для всех, включая CI. Исправлено: диапазон `010–166`, количество 157, обновлены сообщения и контрактный тест `backend/test/verify-script-migration-chain.test.js`.

### D-2. Три shell-скрипта в архиве были с CRLF и не запускались
`scripts/verify.sh`, `backend/test/payment-deletion-receipt-race-concurrency.sh`, `backend/test/run-disposable-concurrency-suite.sh` пришли с переводами строк Windows, из-за чего `bash` падал на `syntax error near unexpected token`. Это ломало один из backend-тестов (1437/1438). В git-версии файлы с LF — дефект появился при упаковке архива; после восстановления файлов из git все 1438 тестов проходят. На будущее: не собирать архив рабочей копией с CRLF-конвертацией.

### D-3. Путаница в корне репозитория
`INSTRUCTIONS.md` в корне — не инструкция по проекту, а заметка о пакетах кредитов Prodamus. Настоящая точка входа — `README.md`. Предлагаю переименовать в `docs/payments-prodamus.md` (или удалить, содержимое уже дублируется в `docs/payments-prodamus.md`).

## 5. План доработки

### Этап 1. Вернуть сервис в рабочее состояние (1 день)
1. Сверить переменные Render с `backend/.env`: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_ANON_KEY`, `JWT_SECRET`, `GPTUNNEL_API_KEY`, `PRODAMUS_*`, `PINTEREST_*`, `MAIL_*`, `FRONTEND_URL`, `PUBLIC_BACKEND_URL`. Проверить, что в значениях нет кавычек, пробелов и `\r` в конце (частая причина «висит 2,5 с»).
2. Перезапустить сервис, добиться `GET /ready` → 200.
3. Пройти вход существующим тестовым аккаунтом; убедиться, что кабинет грузит проекты, баланс кредитов и тариф.
4. Включить внешний мониторинг `/ready` (UptimeRobot, Better Stack или аналог) с проверкой раз в 5 минут — чтобы следующий отказ видели мы, а не клиенты.
5. **Критерий:** `/ready` 200, вход и регистрация работают, мониторинг шлёт алерт на почту.

### Этап 2. Инфраструктура и независимость от провайдеров (3–5 дней)
Цель — размещение ≤ 4000 ₽/мес, без Beget/Timeweb/Yandex/Selectel в критическом контуре, с резервированием.

1. **Backend на Amvera** (Node.js, Docker или git-push): тариф «Начальный» 290 ₽/мес (0,25 CPU, 500 МБ) для API и отдельный «Начальный» для воркеров расписания и удаления аккаунтов. При нагрузке — «Начальный Плюс» 490 ₽/мес.
2. **PostgreSQL на Amvera** (managed, с ежедневными бэкапами) или внешний managed PostgreSQL: 290–490 ₽/мес. Перенос — `pg_dump` из Supabase + восстановление, миграции `001–166` уже проверены на чистой базе (см. §2).
3. **Фронтенд:** статика на Amvera (CDN) вместо Vercel — снимает зависимость от внешнего билд-лимита, который сейчас блокирует деплой. Либо Cloudflare Pages как независимый от РФ-провайдеров слой.
4. **DNS и почта вне Beget:** DNS — Cloudflare (бесплатно) или deSEC; почта — Яндекс 360 / Mail.ru для домена или независимый SMTP (Resend/Brevo для транзакционных писем, если РФ-доставляемость не критична). Домен остаётся у регистратора до успешной миграции; перенос — только после проверки MX/SPF/DKIM/DMARC.
5. **Storage:** Supabase Storage → S3-совместимое хранилище Amvera/VK Cloud (или отдельный бакет), с тестом восстановления объектов.
6. **Резервные копии:** ежедневный `pg_dump` + Storage-манифест, хранение 14 дней в отдельном месте, **обязательная проверка восстановления** раз в месяц. Без проверки восстановления бэкап не считается бэкапом.
7. **Критерий:** сервис работает на новой инфраструктуре, старые ресурсы не удалены, есть проверенный откат, месячный счёт ≤ 4000 ₽.

Ориентир по бюджету (проверить актуальные цены на amvera.ru): backend 290 + worker 290 + Postgres 290–490 + статика 170–290 ≈ 1040–1360 ₽/мес, остальное — запас на Storage и почту.

### Этап 3. Стабильность и наблюдаемость (2 дня)
- Структурированные логи с request-id, единый формат ошибок, запрет `console.log` с данными пользователей.
- Health/readiness в мониторинге, алерты на 5xx > 1 %, на рост очереди писем и на неудачные публикации.
- Автоматическая проверка после деплоя: `/ready`, `/billing/health`, вход тестовым аккаунтом.
- Sentry (или аналог) для фронтенда и бэкенда.

### Этап 4. Продуктовые доделки (по результатам E2E)
Проверить и починить по факту, не «на глаз»:
- регистрация → подтверждение почты → вход → онбординг → создание проекта → анализ сайта → генерация досок → генерация пинов → утверждение → планирование → публикация;
- пустые состояния, ошибки сети, повторные запросы, мобильная вёрстка;
- мультиязычность (7 локалей) — вычитать русский и английский, остальные проверить на подстановку;
- кредиты: списание/резерв/возврат, отрицательный баланс невозможен;
- тарифы и оплата: демо-платёж Prodamus, затем реальный минимальный платёж с возвратом.

### Этап 5. Чистота проекта
- `docs/`: 470 файлов, из них 383 — сессионные заметки в `docs/audits` (3,6 МБ), `PROJECT_STATE.md` 936 КБ, `USER_ACTIONS.md` 436 КБ, `HANDOFF.md` 524 КБ. Смысла в них мало: это в основном повторяющиеся записи «проверил CI, runner не выделен». Предлагаю: перенести всё старше 2026-11-18 в `docs/archive/`, оставить один актуальный `docs/STATUS.md` (этот документ + чек-лист) и один `docs/USER_ACTIONS.md` с живыми задачами.
- Удалить из рабочих копий `.agent-verify/` (271 МБ), `.agent-merge/` (14 МБ), логи `pinposy-staging-*.log` в корне — в git их нет, они попали только в архив.
- Переименовать `frontend/src/data/mockData.ts` → `types.ts` (сейчас это только типы; неиспользуемые константы `INITIAL_ACCOUNTS`, `INITIAL_BOARDS`, `INITIAL_SCHEDULED_PINS`, `PRESET_ACCOUNTS_TO_ADD` удалить — в UI они не используются, но имя файла пугает аудиторов и создаёт ложное впечатление демо-данных).
- Разбить чанк `index` (958 КБ) динамическими импортами: кабинет, тарифы, календарь.
- В архив для передачи больше не включать `.git`, `node_modules`, `.env`, логи.

## 6. План тестов

**Уже есть и проходит (локально, 2026-11-21):** 1438 backend-тестов, 426 frontend-тестов, 51 SQL-интеграционный тест, полная цепочка миграций.

**Чего не хватает:**
1. **E2E «путь нового пользователя»** (Playwright): регистрация → письмо (тестовый SMTP) → вход → проект → доска → пин → утверждение → расписание. 1 сценарий на локальном стенде, 1 на staging.
2. **Контрактные тесты API:** каждый маршрут — успех, 401, 403, 422, 500; отдельно проверка, что пользователь A не читает данные пользователя B (в репозитории есть `data-access-boundary-contract.test.js`, нужно расширить на все таблицы).
3. **Тесты платежей:** вебхук Prodamus — повтор, подпись, чужая сумма, отмена (есть `credits-webhook.test.js`); добавить реальный демо-платёж в staging как ручной чек-лист.
4. **Тесты восстановления:** падение backend в середине генерации, падение worker, просроченное задание расписания, повтор после сбоя Storage.
5. **Smoke после деплоя** (`scripts/smoke-backend.sh` уже есть): расширить на `/ready`, `/billing/health`, вход тестовым аккаунтом, создание проекта.
6. **Регрессия «свежая БД»**: то, что я прогнал сегодня (миграции + 51 SQL-тест), закрепить в CI как обязательный job — иначе дрейф миграций снова сломает verify.
7. **Проверка бэкапа:** ежемесячный тест «взять дамп, поднять на пустой базе, сравнить количество строк по таблицам».
