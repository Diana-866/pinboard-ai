# Настройка фоновой публикации Pinterest

## Пользовательское API расписания

- `GET /schedule` — возвращает расписание только текущего пользователя, включая записи со статусом `cancelled`, чтобы календарь мог показывать историю отмен и фильтровать её отдельно.
- `POST /pins/:id/schedule` — создаёт задание после проверки владельца локального пина, сохранённого изображения, даты/времени, IANA timezone, ссылки и формата ID доски Pinterest. Для вызова требуется активный тариф Start, Pro или Agency.
- `POST /schedule/:id/cancel` — отменяет только запись текущего пользователя в статусе `scheduled`; задание, уже забранное worker'ом в `publishing`, отменить нельзя.

Доступность выбранной доски проверяется дважды: при создании расписания и повторно непосредственно перед публикацией worker'ом. Это отклоняет устаревший или чужой ID заранее и учитывает, что владелец мог удалить доску либо отозвать доступ после планирования. Если аккаунт Pinterest отключён до запуска worker'а, публикация завершается `failed` до создания удалённого пина; если журнал попыток недоступен или результат удалённого запроса неоднозначен, задание остаётся `unknown` и не повторяется автоматически.


## Граница отключения и отмены

Отключение Pinterest атомарно инвалидирует незавершённые OAuth-попытки и удаляет сохранённые в PinPosy токены. После этого новые запросы к Pinterest от имени пользователя не должны начинаться. Однако отключение не может отозвать HTTP-запрос, который backend уже отправил внешнему API: если запрос на создание пина успел уйти до отключения, Pinterest ещё может завершить его. В таком редком случае итог публикации определяется ответом Pinterest и журналом попыток; при неоднозначном ответе повторная отправка блокируется статусом `unknown`.

Также текущий endpoint отключения удаляет локальные credentials, но не выполняет отдельный отзыв OAuth-разрешения на стороне Pinterest. Поэтому «отключить» здесь означает прекратить использование сохранённого доступа PinPosy, а не гарантированно отозвать разрешение в настройках Pinterest.

## Текущая реализация

Backend предоставляет внутренний endpoint:

`POST /internal/pinterest/schedule/run`

Он:
1. Проверяет отдельный секрет `PINPOSY_SCHEDULER_SECRET` через заголовок `x-pinposy-scheduler-secret`.
2. Атомарно забирает ровно одну готовую запись расписания через PostgreSQL RPC `claim_due_pin_schedules` (backend принудительно задаёт `limit = 1`, независимо от тела запроса; конкурентные worker'ы защищены атомарным claim).
3. Публикует пин только если у записи указан `pinterest_board_id`.
4. Сохраняет подтверждённый Pinterest ID и статус `published`.
5. Не повторяет автоматически публикации с неопределённым результатом. Такие записи получают статус `unknown` и требуют сверки, чтобы не создавать дубликаты.

## Переменные окружения

В backend-хостинге нужно добавить:

- `PINPOSY_SCHEDULER_SECRET` — случайная строка не короче 32 байт. Создать её в менеджере секретов/генераторе паролей и сохранить только в настройках backend и cron-провайдера.
- Уже существующие `PINTEREST_CLIENT_ID`, `PINTEREST_CLIENT_SECRET`, `PINTEREST_REDIRECT_URI`.
- Уже существующие серверные переменные Supabase.

Не отправлять секрет в чат, репозиторий, frontend или URL.

## Шифрование OAuth-токенов

Pinterest access/refresh tokens шифруются на backend с помощью AES-256-GCM до записи в существующие текстовые поля таблицы `pinterest_accounts`. Для этого обязательно задайте `PINTEREST_TOKEN_ENCRYPTION_KEY` — ровно 32 случайных байта, закодированных в base64 или 64 hex-символа.

Сгенерировать ключ можно локально:

```bash
openssl rand -base64 32
```

Сохраните значение только в менеджере секретов backend-хостинга. Не добавляйте его в Git, frontend или чат. При первом чтении старые plaintext-строки автоматически перезаписываются зашифрованными значениями. Если ключ потерян, ранее сохранённые токены нельзя будет расшифровать — храните резервную копию ключа в отдельном защищённом месте. Ротацию ключа нельзя выполнять простой заменой значения: сначала нужна отдельная процедура расшифровки старым ключом и повторного шифрования новым.

## Внешний cron

> **Не включать production cron по этому документу в отрыве от согласованного релиза.** Старые выборочные диапазоны миграций ниже больше не являются достаточным списком для текущей версии worker.

Ветка содержит последовательность миграций вплоть до `123`. После миграций `063–120` менялись журнал генерации и перегенерации, резервирование кредитов, публикационные попытки, восстановление расписаний, хранение изображений, платёжные операции и ручная очередь проверки. Поэтому нельзя считать, что для актуального backend достаточно выборочно применить только `015–017`, `026–028`, `031–052` и `056–062`: более поздние миграции изменяют и дополняют те же SQL-контракты, которые использует worker.

**Безопасный порядок подготовки:**

1. Для новой пустой тестовой БД используй только канонический порядок из [инструкции по базе данных](../database.md): `001_baseline.sql`, затем все доступные миграции `010–123` строго по номеру, по одному файлу.
2. Для существующей БД не запускай baseline и не применяй весь диапазон вслепую. Сначала сделай резервную копию, read-only снимок схемы и список уже применённых миграций; затем проверь точный delta-набор на отдельной staging-копии.
3. Проведи PostgreSQL integration tests и backend regression tests на том же commit, который планируется развернуть. Убедись, что backend, SQL-функции и worker относятся к одному согласованному релизу.
4. До включения cron настрой мониторинг возраста просроченных `scheduled`, зависших `publishing`, записей `unknown` и heartbeat самого cron. Один только HTTP-ответ worker не заменяет сверку очереди и журнала попыток.
5. Только после успешного staging-прогона, настройки секретов, резервного копирования ключа шифрования и отдельного подтверждения владельца включай **один** production scheduler.

### Выбери только один способ запуска

**Вариант A — отдельный worker-процесс (предпочтительный для постоянной работы).**

В отдельном worker-сервисе из того же согласованного backend commit запусти:

```bash
npm ci
npm run worker
```

Передай ему:
- `PINPOSY_BACKEND_URL=https://<backend-host>` (либо `PUBLIC_BACKEND_URL`);
- `PINPOSY_SCHEDULER_SECRET` — тот же секрет, что настроен в backend.

Worker сам обращается к защищённому endpoint каждые 30 секунд по умолчанию, отправляет только `limit: 1`, не допускает перекрывающихся запросов и корректно завершает работу при SIGTERM/SIGINT. Интервал можно задать через `PINPOSY_SCHEDULER_INTERVAL_MS`. Не запускай worker внутри нескольких реплик backend: для него нужен один выделенный процесс; защита claim в БД остаётся последним барьером от конкурентной публикации.

**Вариант B — внешний cron / scheduler-провайдер.**

Если отдельный worker-процесс не используется, внешний scheduler может вызывать endpoint по HTTPS примерно раз в минуту:

- Method: `POST`
- URL: `https://<backend-host>/internal/pinterest/schedule/run`
- Header: `x-pinposy-scheduler-secret: <secret>`
- JSON body: `{"limit":1}`

Backend в любом случае принудительно обрабатывает не более одной записи за запрос; переданный лимит не управляет размером claim.

**Не включай одновременно вариант A и вариант B.** Это создаст лишние параллельные пробуждения очереди и усложнит диагностику, хотя атомарные claim и fencing должны предотвращать двойное получение одной записи.

При таймауте сначала проверь `pin_schedules` и `pinterest_publish_attempts`, а не отправляй публикацию повторно вручную. Записи `unknown` нельзя автоматически переводить в `scheduled`: их нужно сверить в Pinterest и восстановить только по подтверждённым данным.

## Heartbeat планировщика — реализация в main, staging validation pending

`main` содержит migration `122_pinterest_scheduler_health_monitor.sql`, helper `backend/pinterestSchedulerHealth.js` и read-only admin endpoint:

`GET /admin/operations/pinterest-scheduler`

Внутренний маршрут `POST /internal/pinterest/schedule/run` зарегистрирован в `backend/pinterest.js` через `registerRoutes(app, ...)`, который вызывается из `backend/index.js`. После проверки scheduler secret маршрут вызывает `begin_pinterest_scheduler_run`, выполняет штатный fenced claim/publish flow и фиксирует агрегированный итог через `complete_pinterest_scheduler_run`. Run UUID не позволяет запоздавшему завершению перезаписать запись более нового запуска; begin RPC блокирует перекрывающийся запуск в пределах 20 минут.

**Важно:** наличие кода не означает, что migration уже применена или worker реально работает в production. Применение миграций 122–123 к production Supabase не подтверждено; runtime tests, SQL integration, lint/build/CI и provider dashboard не проверялись. До production rollout нужны staging-прогон migration 122 и backend tests на одном commit, проверка admin status и отдельное подтверждение владельца.

После завершения интеграции ожидаемая модель статусов:
- `not_seen` — ни одного запуска не зафиксировано;
- `running` — запуск начался менее 20 минут назад;
- `healthy` — последний запуск завершился успешно, завершение моложе 3 минут;
- `failed` — последний запуск завершился ошибкой, завершение моложе 3 минут;
- `stale` — завершённый запуск старше 3 минут, незавершённый запуск старше 20 минут или timestamp некорректен.

Heartbeat будет подтверждать вызов scheduler endpoint, но не доступность Pinterest API и не отсутствие зависших публикаций. Его нужно сверять с просроченными `scheduled`, зависшими `publishing` и `unknown` записями. Публичный `/health` остаётся только liveness-проверкой API.

## Однократный Cron runner

Для провайдера, который запускает команду по расписанию (например, Cron Job), в backend добавлен отдельный одноразовый entrypoint:

```bash
npm run cron:schedule
```

Каждый запуск делает ровно один HTTPS-запрос к `/internal/pinterest/schedule/run`, передаёт секретный заголовок, проверяет структуру ответа и завершает процесс. Запрос не следует за HTTP-редиректами; временные HTTP-агенты закрываются и при успехе, и при ошибке. Ошибка или некорректный ответ завершают процесс с ненулевым exit code, чтобы Cron-провайдер мог отметить запуск как неуспешный.

Переменные окружения Cron Job:
- `PINPOSY_BACKEND_URL=https://<backend-host>` — только origin backend, без пути;
- `PINPOSY_SCHEDULER_SECRET` — тот же случайный секрет длиной не менее 32 символов, что задан в backend.

Рекомендуемая частота — раз в минуту, с запретом параллельных запусков на стороне Cron-провайдера. Один вызов обрабатывает максимум одну публикацию. Если очередь пуста, вызов штатно завершается с нулём обработанных записей. Не запускай одновременно `npm run worker` и `npm run cron:schedule`: выбери один способ пробуждения очереди.

Команда и тесты добавлены в PR #78. До прохождения проверок на целевом commit и staging-проверки SQL/публикации не включай production Cron.

## Проверки перед отправкой

Перед каждой реальной отправкой worker повторно проверяет активность тарифа пользователя. Доступны только тарифы `start`, `pro` и `agency`; если подписка истекла или тариф не подходит, запись переводится в `failed` с причиной, а публикация не отправляется.

Перед резервированием backend проверяет выбранную доску запросом Pinterest `GET /boards/{board_id}` от имени того же подключённого аккаунта. Для запланированной публикации используется `destination_url`, сохранённый в календаре; если пользователь не указал ссылку, используется адрес сайта проекта (если он задан).

## Восстановление старых расписаний без аккаунта

Migration 052 добавляет RPC `reconcile_legacy_pinterest_schedule_account`. В календаре для старого расписания со статусом ошибки и пустым `pinterest_account_id` можно запустить восстановление. Backend получает список активных подключённых аккаунтов пользователя, проверяет выбранный аккаунт и отдельно запрашивает у Pinterest сохранённую доску именно от его имени. Только после успешной проверки SQL-функция атомарно привязывает расписание к этому аккаунту и возвращает его в очередь.

Правила выбора:
- один активный аккаунт — он предлагается как единственный кандидат, но восстановление всё равно запускается явным действием пользователя;
- несколько активных аккаунтов — требуется выбрать конкретный аккаунт;
- нет активных аккаунтов — сначала нужно подключить Pinterest;
- сохранённая доска отсутствует или недоступна выбранному аккаунту — восстановление отклоняется.

SQL дополнительно блокирует привязку, если исходный пин не одобрен, по нему уже есть любая запись в журнале попыток или реестр публикаций, если расписание уже обрабатывается/завершено либо если для этого пина уже существует активное расписание в выбранном аккаунте. Такие случаи требуют ручной сверки; новая идентичность не назначается автоматически. Миграция 052 должна быть применена до использования нового endpoint.

## Снимок контента при планировании

Migration 051 добавляет в `pin_schedules` неизменяемые поля `snapshot_title`, `snapshot_description`, `snapshot_image_url` и `snapshot_destination_url`. Новое расписание фиксирует заголовок, описание, URL изображения и итоговую ссылку назначения (явную ссылку или сайт проекта). Последующее редактирование пина или сайта проекта не меняет уже запланированную публикацию. Изображения загружаются в уникальные storage-пути, поэтому сохранённый URL продолжает указывать на исходный файл.

Старые записи до migration 051 остаются без snapshot и продолжают использовать прежнее поведение: worker публикует текущую версию пина. Для фиксации старого контента пользователь может отменить расписание и создать его заново.

## Единая политика безопасного повтора

Migration 050 добавляет в attempt journal поле `retry_safe`. Оно выставляется только серверной функцией фиксации отказа, если worker установил, что Pinterest create request не мог создать удалённый пин. Для неоднозначного результата выставляется `unknown`, а повтор блокируется. Если параметр классификации не передан, SQL RPC по умолчанию выбирает `unknown`.

- Direct publish и scheduled worker используют один `begin_pinterest_publish_v2`: повтор существующей попытки разрешён только при `status='failed' AND retry_safe=true`.
- Manual retry проверяет тот же флаг. Если attempt отсутствует, повтор допустим; если журнал существует, но флаг false, повтор запрещён.
- После начала нового повтора `retry_safe` атомарно сбрасывается в false и attempt возвращается в `processing`.
- Исторические `failed` записи получают `retry_safe=false` по умолчанию. Их нельзя автоматически считать безопасными только из-за старого статуса.

## Fencing и восстановление claim

После migration 049 каждая запись, полученная worker'ом, имеет отдельный UUID `claim_token`. До создания attempt journal worker обязан передать этот token в `begin_scheduled_pinterest_publish`; функция проверяет, что worker всё ещё владеет именно этой записью. Запоздавший worker с отозванным token не может зарезервировать публикацию и отправить Pinterest POST.

Если claim старше 20 минут:
- при отсутствии attempt journal token инвалидируется, schedule возвращается в `scheduled` с задержкой 1 минута;
- если attempt journal уже существует, запись остаётся `unknown` (кроме подтверждённого успеха, который восстанавливается в `published`).

Наличие attempt journal — консервативная граница неопределённости: после её создания PinPosy не может доказать, что внешний POST точно не ушёл, поэтому автоматический повтор запрещён. Migration 049 должна быть применена до развёртывания backend-кода, который вызывает новый RPC.

## Проверки восстановления

PostgreSQL integration test проверяет:
- повторную резервацию уже опубликованного локального пина без нового remote ID;
- перевод зависшей попытки `processing` в `unknown` после 15 минут;
- возможность сохранить поздний успешный ответ Pinterest в ранее неопределённую попытку;
- восстановление расписания в `published`, если журнал публикаций уже содержит подтверждённый Pinterest ID;
- перевод зависшего расписания без подтверждённого remote ID в `unknown`, а не в повторную очередь.

Эти проверки описывают ожидаемое поведение SQL-функций. Они не заменяют реальную проверку Pinterest API и считаются пройденными только после успешного выполнения CI.

## Важные ограничения

- Этот endpoint пока не настроен в production и не вызывается внешним cron.
- Миграции 015, 016 и 017 пока не применены к рабочей базе.
- Шифрование Pinterest access/refresh tokens уже реализовано в backend. До подключения реальных пользователей необходимо задать `PINTEREST_TOKEN_ENCRYPTION_KEY` в настройках backend и сохранить его резервную копию в отдельном защищённом месте; старые plaintext-токены будут перешифрованы при первом чтении после установки ключа.
- До публичного запуска также необходимо проверить Pinterest Standard Access и провести тестовую публикацию на отдельной доске.
- Статус `unknown` нельзя автоматически переводить в `scheduled`: сначала нужно проверить, появился ли пин в Pinterest.
- Убедиться, что сохранённые image_url доступны Pinterest по HTTPS без авторизации и редиректов, которые Pinterest не может обработать.


## Загрузка списка досок

Список досок Pinterest загружается с cursor pagination: до 8 страниц по 250 записей (лимит Pinterest — 2 000 досок). Если API вернёт продолжение за пределами этого лимита, backend сообщает об ошибке вместо того, чтобы молча показать неполный список.


## Heartbeat планировщика — подключён в backend, требует применения миграций 122–123

Внутренний endpoint `POST /internal/pinterest/schedule/run` находится в `backend/pinterest.js` и регистрируется из `backend/index.js` через `registerRoutes()`. Отдельный процесс `backend/scheduleWorker.js` обращается к нему каждые 30 секунд по умолчанию.

Endpoint:
- проверяет `PINPOSY_SCHEDULER_SECRET` timing-safe сравнением заголовка `x-pinposy-scheduler-secret`;
- фиксирует начало/завершение heartbeat через RPC;
- выполняет reconciliation только подтверждённых публикаций;
- забирает не более одной записи за вызов;
- продлевает claim, проверяет тариф и вызывает существующий `publishPin()`;
- сохраняет агрегированные счётчики без публикационных идентификаторов и секретов.

Migration 122 создаёт таблицу мониторинга и RPC. Migration 123 делает завершённый запуск терминальным: повторное завершение не может перезаписать уже сохранённый результат, а UUID старого запуска не может завершить новый.

**Rollout:** миграции 122–123 уже находятся в `main`, но их применение к production Supabase не подтверждено. До запуска worker/cron требуются staging-прогон точной последовательности миграций и backend на одном commit, Node/PostgreSQL integration tests, проверка секретов и отдельное подтверждение владельца. В production должен работать только один способ пробуждения очереди — отдельный worker ИЛИ внешний cron.

Статусы admin health: `not_seen`, `running`, `healthy`, `failed`, `stale`. Heartbeat подтверждает вызов endpoint, но не доступность Pinterest API и не заменяет сверку `scheduled/publishing/unknown`.
