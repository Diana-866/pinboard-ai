## 1. Что строим

PinPosy — мультиязычный SaaS для планирования и создания контента Pinterest. Пользователь регистрируется, создаёт проекты на основе своего сайта/ниши, генерирует доски и пины, редактирует и вручную утверждает их, планирует публикации, подключает один или несколько Pinterest-аккаунтов, публикует контент, отслеживает результаты и оплачивает тарифы/кредиты.

Сервис рассчитан не только на пользователей из России. Важны безопасность пользовательских данных, отсутствие потери оплаченных результатов, корректная работа с несколькими аккаунтами Pinterest и устойчивость к сетевым сбоям.

## 2. Как читать статусы и считать проценты

Каждый пункт — отдельное проверяемое требование.

- `[ ]` — не сделано или не доказано.
- `[~]` — реализация/часть реализации есть в коде или документации, но полный критерий приёмки ещё не подтверждён тестами и/или staging-проверкой.
- `[x]` — критерий полностью выполнен и подтверждён актуальными тестами или воспроизводимой проверкой.
- `[!]` — заблокировано внешним решением, доступом, ключом или действием владельца. До снятия блокера в прогресс не засчитывается.

**Формула прогресса:** `(число [x] + 0,5 × число [~]) / общее число пунктов × 100%`. Все пункты внутри одного реестра имеют одинаковый вес. Пункты [!] входят в знаменатель и дают 0, пока блокер не снят. Процент округляется до одного знака после запятой. Нельзя менять статусы ради красивого процента.

Отчёты всегда показывают отдельно:
1. **Продукт без инфраструктурного переноса** — этот документ.
2. **Инфраструктура** — отдельный документ.
3. **Общий прогресс** — сумма баллов двух реестров / сумма пунктов обоих реестров. Так инфраструктура не исчезает из общей оценки, но остаётся отдельным этапом.

Нельзя ставить [x] только потому, что код написан. Нужны успешные актуальные проверки. Если CI недоступен, статус остаётся [~] или [ ] с явной пометкой о причине.

## 3. Подтверждённые продуктовые решения и ограничения

- Название продукта: **PinPosy**.
- Основной сценарий: создание и планирование Pinterest-контента с AI.
- Технологический кодовый стек на текущем этапе: React 19 + Vite + TypeScript, Express 4 / Node.js, PostgreSQL/Supabase, GPTunnel, Pinterest API, Prodamus.
- Вход через Google ранее отменён владельцем. Основной способ — e-mail + пароль.
- Тарифные идентификаторы в коде/схеме: `none`, `analytics`, `start`, `pro`, `agency`.
- Пакеты кредитов, ранее утверждённые для модели продаж: 100 / 500 / 1000 кредитов за 190 / 790 / 1290 ₽. Текущую экономику и отображаемые цены требуется сверить перед продажей.
- Планируемый платёжный провайдер — Prodamus; кодовая интеграция не означает, что реальные платежи включены.
- Pinterest API используется официальным способом; сбор чужих приватных данных и скрейпинг Pinterest не допускаются. Функции аналитики конкурентов должны использовать только законные и разрешённые источники.
- Никаких production merge/deploy, production SQL migrations, DNS-переключений, реальных списаний/возвратов или публикаций без отдельного явного согласования.
- Точные квоты тарифов, стоимость анализа сайта/генерации текстового плана и некоторые лимиты требуют отдельной продуктовой/финансовой фиксации; не вводить скрытые списания или ограничения.

## 5. Текущая стартовая фиксация — что уже сделано

Ниже отмечена реализация, которую можно подтвердить по текущему коду/документации. Это **не означает**, что соответствующая функция уже прошла полный CI, staging или production acceptance. Поэтому соответствующие пункты остаются [~], а не [x].

### Основные реализованные направления
- Backend API для проектов, досок, пинов, кредитов, Pinterest accounts/publications и расписания.
- Server-side генерация через GPTunnel, idempotency keys, fingerprints, generation journal, recovery states и атомарное списание/резервирование кредитов.
- Постоянное хранение изображений и восстановление результатов из Storage в предусмотренных сценариях.
- Persisted boards: загрузка досок из API, создание с ожиданием ответа сервера, защита от повторного submit и сохранение введённого названия при ошибке.
- Idempotent board creation и SQL regression сценарии (migration 111).
- Persistent schedule API, календарная загрузка, отмена, retry/reconciliation и Pinterest worker groundwork.
- Защита Pinterest publication attempts от дубликатов/неопределённого результата; шифрование OAuth токенов AES-256-GCM.
- Prodamus webhook/billing code и документация; реальная конфигурация/платёжный запуск требуют проверки.
- Изоляция состояния Pinterest generator при смене пользователя (AUD-301).
- Защита от устаревших сохранений и гонок редактирования пинов/досок (AUD-302—305).
- Изоляция календарного состояния при смене пользователя (AUD-306).
- Изоляция in-memory очереди ручной проверки при смене пользователя (AUD-307), но **постоянное восстановление этой очереди ещё не реализовано**.

4. Worker/cron, реальные Pinterest credentials/scopes и тестовая публикация не подтверждены.
5. Prodamus code не равен успешно проверенному реальному/демо-платежу.
6. Не завершён полный RLS/security review и end-to-end тест изоляции двух пользователей.
7. Аналитика/конкуренты/квоты и экономика ряда AI-операций требуют подтверждённой спецификации.
8. Целевая инфраструктура, независимые backups и restore drill не подключены/не подтверждены.
9. Юридические документы, email deliverability, мониторинг, load test и публичный запуск требуют финальной проверки.

## 7. Правила обновления этого реестра

- Перед каждым новым этапом читать этот файл и проверять текущий HEAD/PR/CI.
- Исправлять продукт, а не ограничиваться написанием аудита.
- Каждый найденный дефект получает ID, тест/критерий приёмки и ссылку на изменение.
- После изменения обновлять статус соответствующего пункта и журнал.
- [~] переводить в [x] только после фактического прохождения критерия на актуальном коде.
- Если требование меняется, записывать причину/дату и сохранять историю; не удалять незаметно старые обязательства.
- Новые требования добавлять с уникальным ID, не дробить/объединять пункты только ради изменения процента.
- В каждом отчёте указывать: продукт %, инфраструктура %, общий %, выполнено/частично/осталось, что реально проверено, что не проверено, какие действия нужны от владельца.
- Если задача требует доступа владельца, не останавливать всю автономную работу: зафиксировать blocker и продолжать независимые задачи.
- Инфраструктурные задачи выполнять по отдельному документу [INFRASTRUCTURE_REQUIREMENTS.md](./INFRASTRUCTURE_REQUIREMENTS.md).
