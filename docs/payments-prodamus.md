# Приём платежей PinPosy через Prodamus — рабочая инструкция

Документ написан для человека, который **никогда не работал с Prodamus** и **не имеет статуса самозанятого**.
Здесь: как это устроено в коде, какие переменные окружения нужны на Render, как прогнать демо-платёж
и что делать с юридической стороной (включая приём платежей из других стран).

### Схема потока

1. Пользователь жмёт «Выбрать тариф «Старт»» → `POST /billing/create-payment`.
2. Бэкенд создаёт строку в `subscriptions` (`status = pending`, `provider_payment_id = pp-start-...`)
   и просит у Prodamus ссылку (`do=link`).
3. Браузер уходит на `https://<shop>.payform.ru/...`. Пользователь платит картой.
4. Prodamus шлёт `POST /billing/webhook` (`application/x-www-form-urlencoded`, подпись в заголовке `Sign`).
5. Бэкенд проверяет подпись → находит строку по `order_id` → PostgreSQL атомарно активирует подписку, обновляет тариф и добавляет событие письма в `email_outbox`.
6. Dispatcher забирает событие и отправляет локализованное письмо через Unisender Go SMTP; после подтверждения SMTP помечает событие `sent`.
7. Пользователь возвращается на `/app?payment=success`, фронт опрашивает `/me` (0/3/8/15 с) — замочки снимаются.

## 2. Миграции

`006_subscriptions.sql` и `007_credit_purchases.sql` создают исходные таблицы подписок и покупок кредитов. Для текущей версии backend требуется применить **все необходимые миграции из `db/migrations` строго по возрастанию номера**, а не только 006/007.

В частности, миграции 010/011 обеспечивают атомарное зачисление кредитов и активацию подписки; 019 защищает тариф от запоздавших вебхуков; 026–028 защищают обновление Pinterest-токенов и OAuth; 029 создаёт журнал исключений платёжных вебхуков; **030 добавляет transactional email outbox**.

Миграция 029 должна быть применена **до развёртывания backend**, который записывает в `billing_webhook_exceptions`. Она хранит минимальные данные для сверки: тип платежа, order_id, статус, полученную и ожидаемую сумму, причину и SHA-256 отпечаток события (служебный `attempt`, номер доставки, исключается из отпечатка, чтобы повторы не создавали новые записи). Полный payload и email клиента в эту таблицу не записываются. Повторная доставка того же подписанного события не создаёт дубликат.

Миграции 029 и 030 должны быть применены **до развёртывания соответствующего backend-кода**. 030 заменяет `activate_paid_subscription`: запись события активационного письма создаётся в той же транзакции, что и тариф; dispatcher использует lease, повторы с backoff и очищает email/payload после подтверждённой отправки. Если SMTP не настроен, очередь остаётся нетронутой. Отправка не exactly-once: при сбое между SMTP acceptance и фиксацией `sent` возможен дубликат.

Не применять 029/030 поверх неизвестной схемы: сначала проверить текущую версию базы и применённые миграции. В рамках текущей разработки миграции только добавлены в репозиторий и CI; **в Supabase они не применялись**.

| `SUPABASE_SERVICE_ROLE_KEY` | да (уже есть) | service_role key (не anon!) |
| `JWT_SECRET` | да (уже есть) | текущий секрет |

| `PRODAMUS_SYS` | нет для самописной интеграции | код интеграции от поддержки Prodamus; backend всегда передаёт обязательное поле `sys`. Для самописных систем допустимо пустое значение, если отдельный код интеграции не выдан |
| `PRODAMUS_DEMO` | нет | `1` — все платежи идут в демо-режиме |
| `PRODAMUS_OFFLINE` | нет | `1` — не ходить в сеть (только локальные тесты) |

| `MAIL_SMTP_HOST` / `MAIL_SMTP_PORT` / `MAIL_SMTP_USER` / `MAIL_SMTP_PASS` / `MAIL_FROM` | да для писем | отдельные переменные транзакционного SMTP; без них outbox не забирает письма и сохраняет их в очереди до настройки SMTP |
| `ALLOW_TARIFF_SELF_SELECT` | нет | `1` — разрешить ручную смену тарифа (по умолчанию в production запрещено, кроме админа) |
| `NODE_ENV` | да | `production` на Render |

`GET /billing/health` покажет, всё ли подхватилось:
`{"configured":true,"demo":false,"webhook_url":"https://…/billing/webhook"}`.

## 4. Проверка в демо-режиме Prodamus (критерий задачи)

1. В кабинете Prodamus включите демо-режим / работайте на тестовой платёжной форме.
2. На Render: `PRODAMUS_DEMO=1`, `PRODAMUS_SHOP_ID`, `PRODAMUS_SECRET`, `PUBLIC_BACKEND_URL`.
3. Проверьте текущую схему и примените все отсутствующие миграции строго по возрастанию номера, включая 006–030 (не запускайте 006 повторно вместо проверки состояния).
4. Зарегистрируйтесь на сайте, войдите, откройте «Тарифы» → «Выбрать тариф «Старт»».
5. В Supabase появится строка `pending`. Оплатите на странице Prodamus тестовой картой.
6. После оплаты:
   - в `subscriptions` строка станет `success` с `period_start` и `period_end`;
   - в `users` → `tariff_plan = start`, `tariff_period_end` ≈ +30 дней;
   - придёт письмо «тариф активирован»;
   - на `/app` замочки исчезли; в админке вкладка «5. Подписки и платежи» показывает платёж.

### Если вебхук не пришёл

- Проверьте `GET /billing/health` → `webhook_url`.
- В кабинете Prodamus укажите этот URL как адрес уведомлений (и/или заполните `PRODAMUS_SYS`).
- Логи Render: `[billing] вебхук отклонён: …` — значит не совпала подпись.
  Тогда переключите `PRODAMUS_SIGN_PHP_ESCAPE=0` и повторите платёж: разные версии API
  экранируют `/` по-разному. Код уже пробует оба варианта автоматически, но
  переменная помогает, если и это не сработало.
- Prodamus повторяет уведомление при не-200 ответе. Повторный `success` идемпотентен:
  второй раз тариф не продлевается (проверено тестом).

### Локальная проверка без Prodamus и без Supabase

```
cd backend && node ../test/billing-flow.js
```

Тест проверяет: создание `pending`, каноническую строку подписи, активацию на 30 дней,
идемпотентность, отказ при плохой подписи, отказ «Аналитике» в генерации, алиас `standard → pro`,
блокировку после истечения периода.

## 5. Правило тарифов

- `analytics` — только аналитика, генерация закрыта (и в UI, и на API).
- `start` / `pro` / `agency` — генерация открыта (`/boards/:id/pins/generate`,
  `/pins/:id/regenerate`, `/projects/:id/boards/generate`).
- `standard` — старое имя «Про»: алиас на `pro` (миграция 004 переименовала его).
- Тариф активен только пока `period_end` в будущем; после истечения API отдаёт
  `403 { code: "tariff_required" }`.

## 6. Юридическая часть: чего Prodamus требует и что делать без самозанятости

### 6.1. Что нужно Prodamus

Prodamus — российский платёжный сервис: подключение доступно **самозанятым (НПД), ИП и ООО,
зарегистрированным в РФ**. Самозанятым отдельно удобно: не нужна онлайн-касса, чеки уходят
в «Мой налог» автоматически. ([prodamus.ru/questions](https://prodamus.ru/questions),
[prodamus.ru/priem-platezhej-dlya-samozanyatyh](https://prodamus.ru/priem-platezhej-dlya-samozanyatyh))

Единоразовое подключение платёжного модуля — 10 000 ₽ для ИП / ИП на НПД / юрлиц, дальше только
комиссия с платежей ([prodamus.ru, страница для ИП](https://prodamus.ru/priem-platezhej-dlya-individualnogo-predprinimatelya)).

**Вывод:** «нет самозанятости» = нет кабинета Prodamus. Это блокер не в коде, а в статусе.
Три законных пути:

| Путь | Что делать | Плюсы | Минусы |
|---|---|---|---|
| A. Самозанятость (НПД) | Приложение «Мой налог», паспорт + ИНН, 10 минут | Бесплатно, без кассы, без отчётности | Лимит 2,4 млн ₽/год; нельзя нанимать сотрудников; только граждане РФ (иностранцам нужен статус резидента) |
| B. ИП | Регистрация ИП, УСН 6% | Нет лимита 2,4 млн, можно нанимать | Взносы, отчётность, касса при торговле |
| C. ООО | Юрлицо | Работа с B2B, крупные обороты | Дороже в обслуживании |

Лимит НПД 2,4 млн ₽/год — жёсткий: при тарифе «Про» 4 990 ₽ это ≈ 480 оплат в год.
Превысили — теряете НПД с начала превышения
([consultant.ru](https://www.consultant.ru/law/podborki/predelnyj_dohod_samozanyatogo/),
[banki.ru](https://www.banki.ru/news/daytheme/?id=11025827)).
Для SaaS с ростом это значит: **начинать можно с НПД, но планировать переход на ИП**.

### 6.2. Иностранные клиенты (у вас пользователи по всему миру)

Prodamus умеет принимать **зарубежные карты Visa / Mastercard / Maestro в EUR и USD**;
комиссия по таким платежам — **10%**, минимальный платёж 100 ₽, деньги приходят на рублёвый счёт
([prodamus.ru/priem-mezhdynarodnyh-platezhey](https://prodamus.ru/priem-mezhdynarodnyh-platezhey)).
В коде это уже учтено: `currency` в `create-payment` принимает `rub` и `usd`, каталог цен —
`POST /billing/plans`.

Честные ограничения, которые надо понимать заранее:

1. **Не все зарубежные карты проходят.** Это не глобальный эквайринг уровня Stripe: часть
   банков-эмитентов отклоняет платежи в адрес российского мерчанта. Реальный процент успеха
   зависит от страны плательщика и проверяется только практикой — обещать «весь мир» нельзя.
2. **Prodamus заточен под рублёвый расчёт.** Вы получаете рубли, а клиент платит валютой —
   курсовые риски и конвертация на стороне сервиса.
3. **Налоги в стране клиента.** НДС/sales tax для цифровых услуг (EU VAT, UK VAT, налоги штатов США)
   Prodamus за вас не считает и не платит. При продажах физлицам в ЕС это обязанность продавца
   (порог OSS — 10 000 € в год на весь ЕС).

### 6.3. Когда Prodamus не подходит и что вместо него

Если основная аудитория — **не Россия**, а вы хотите, чтобы налоги считал сервис, нужен
**Merchant of Record** (он продавец, он же платит налоги):

| Вариант | Для кого | Важное ограничение |
|---|---|---|
| **Paddle** | SaaS, цифровые продукты, глобальные карты | Работает только с продавцами из поддерживаемых стран; РФ в списке нет ([paddle.com](https://www.paddle.com/help/start/intro-to-paddle/which-countries-are-supported-by-paddle)) |
| **Lemon Squeezy** | инди-разработчики, быстрый старт | Не принимает платежи **от** клиентов из РФ, Беларуси и ряда стран; выплаты — на счёт в поддерживаемой стране ([docs.lemonsqueezy.com](https://docs.lemonsqueezy.com/help/getting-started/supported-countries)) |
| **Stripe** | максимум контроля | Для резидентов РФ недоступен напрямую |
| **ИП/юрлицо в Казахстане, Армении, Грузии + местный эквайринг** | те, кто хочет и РФ, и мир | Нужна реальная регистрация и налоговый резидентств/отчётность в этой стране; «фирма-прокладка» без присутствия — риск блокировки средств |
| **Крипто (USDT) / Payoneer / Wise invoices** | B2B, услуги, аудитория, у которой нет карты | Не карточный эквайринг, конверсия и доверие ниже; в РФ требует аккуратной налоговой трактовки |

Практичная рекомендация для PinPosy:

- **Сейчас (день 1):** самозанятость или ИП в РФ + Prodamus. Код уже готов, приём рублей и
  части зарубежных карт работает.
- **Когда появятся клиенты из ЕС/США:** держать Prodamus для РФ/СНГ и **добавить второй канал**
  (Merchant of Record или компания в стране с доступом к Stripe). Архитектура к этому готова:
  `subscriptions.provider_payment_id` + `status` не привязаны к Prodamus жёстко, `payment_provider`
  в `/me` — поле-заглушка под мультипровайдерность.
- **Не пытайтесь** «принять весь мир одной кнопкой»: ни Prodamus, ни один сервис этого не даёт
  из РФ. Ваш лендинг уже обещает «карты РФ и зарубежные» — формулировка корректна, но добавьте
  мелким шрифтом «доступность зависит от банка-эмитента».

### 6.4. Документы для клиента

Prodamus формирует чек (для НПД — через «Мой налог», для ИП/ООО — через кассу или без неё
в зависимости от режима). Оферту/условия подписки на сайте уже есть (`frontend/src/legal/terms.*`),
в них стоит отразить: срок 30 дней, автопродление отсутствует (продление — ручное, кнопкой
«Продлить тариф»), возврат — по закону о защите прав потребителей.

### Сверка исключений вебхуков

Подписанные уведомления, которые не удалось сопоставить с заказом или сумма которых отличается от ожидаемой, записываются в `billing_webhook_exceptions`. В таблицу не попадают сырые payload и персональные данные клиента. Повторная доставка идентичного события не создаёт новую запись.

Для ручной сверки в Supabase SQL Editor:

```sql
select created_at, payment_kind, order_id, payment_status,
       received_sum, expected_amount, reason, event_hash
from public.billing_webhook_exceptions
order by created_at desc
limit 100;
```

Дальнейшие действия:
1. Найти операцию в кабинете Prodamus по `order_id` и подтвердить фактический статус/сумму.
2. Найти внутренний заказ в `subscriptions` или `credit_purchases`.
3. Если сумма и заказ совпадают, зафиксировать результат сверки и использовать только проверенную процедуру повторной обработки, когда она будет реализована. Сейчас отдельного безопасного replay-инструмента нет: не начислять кредиты и не менять тариф вручную.
4. Если заказ не найден, выяснить причину отсутствия записи и связать платёж с клиентом до любых ручных действий.

Таблица предназначена для сверки через защищённый доступ к БД; отдельный API-эндпоинт для чтения этих записей не предоставляется.

### Возвраты Prodamus: ручная сверка и ограничения

По опубликованной инструкции Prodamus возврат инициируется продавцом из личного кабинета: открыть исходный платёж в «Списке платежей», сформировать полный или частичный возврат и отслеживать его статус там же. Статус «Возвращается» означает, что заявка подана и обрабатывается; только статус «Возвращён» означает, что Prodamus выполнил свою часть возврата и отправил возвратный чек. Prodamus также указывает, что уведомление о возврате отправляется на email, заданный в настройках платёжной страницы. Частичный возврат доступен при включённой функции; в инструкции указана минимальная сумма 100 ₽.

**Важное ограничение интеграции:** текущая опубликованная спецификация обычного платёжного вебхука описывает статусы `success`, `order_canceled` и `order_denied`, но инструкция по возвратам не описывает отдельный webhook/callback с идентификатором, суммой и финальным статусом возврата. Поэтому PinPosy не должен считать заявку на возврат подтверждённой только по факту её создания или по письму без проверки статуса в кабинете.

До появления проверенного машинного источника подтверждения возврата:
1. Сверять возврат в кабинете Prodamus по исходному `order_id`; фиксировать сумму, валюту, дату, полный/частичный характер и финальный статус «Возвращён».
2. Сохранять подтверждающие сведения в защищённом финансовом учёте. Не хранить данные карты и не помещать персональные данные клиента в технический журнал вебхуков.
3. Не менять `subscriptions.status` на `canceled` и не переписывать историю успешного платежа: возврат — отдельное финансовое событие, а не отмена факта оплаты.
4. Не отзывать тариф простым сбросом `users.tariff_plan`: у пользователя могут быть более поздние оплаченные периоды. Нужна отдельная транзакционная процедура, учитывающая порядок и пересечение периодов.
5. Не вычитать купленные кредиты прямым UPDATE и не допускать отрицательный баланс. Для уже потраченных кредитов требуется отдельная политика и атомарный механизм корректировки/долга.
6. Не запускать автоматическое изменение доступа до появления отдельного журнала возвратов, правил полного/частичного возврата и тестов на повторные события и конкурирующие платежи.

Сейчас в PinPosy нет автоматической обработки подтверждённых возвратов и безопасного инструмента их повторного применения. Это сознательное ограничение: лучше провести контролируемую ручную сверку, чем ошибочно отозвать действующий тариф или списать кредиты, которые пользователь уже потратил.

### Конкурентная активация подписок и transactional email outbox

Миграция `019_prevent_late_subscription_downgrade.sql` выполняет активацию внутри одной PostgreSQL-функции. Она блокирует строку подписки (`FOR UPDATE`), затем строку пользователя (`FOR UPDATE`). Для одного пользователя это сериализует применение разных оплаченных заказов: более поздний по созданию оплаченный заказ определяет текущий тариф, а корректный запоздавший платёж может добавить оплаченный период, не заменяя тариф более нового заказа. Повторный вызов для уже активированной строки использует сохранённый `period_end`, поэтому не продлевает один и тот же заказ повторно.

Миграция `030_transactional_email_outbox.sql` расширяет ту же транзакцию: при первой активации подписки создаётся уникальное событие `subscription_activated:<subscription_id>` с адресом получателя, языком и минимальными данными для шаблона. Повторный webhook не создаёт второе событие. Сырые вебхуки и данные карты в outbox не сохраняются.

Dispatcher в `backend/billing.js` забирает события через `claim_email_outbox` с `FOR UPDATE SKIP LOCKED` и lease-токеном. После принятия письма SMTP он вызывает `mark_email_outbox_sent`; при ошибке — `retry_email_outbox` с backoff до 8 попыток, после чего событие становится `dead`. SMTP получает стабильный Message-ID на основе ID подписки.
После подтверждённой отправки функция `mark_email_outbox_sent` очищает адрес получателя и шаблонный payload; в записи остаются статус и технические метаданные. Для событий `dead` адрес сохраняется до ручной сверки, поэтому к таблице допускается только backend service role; отдельная политика очистки старых dead-событий потребуется перед длительной эксплуатацией.

**Гарантия доставки не exactly-once.** Если SMTP принял письмо, а процесс остановился до фиксации `sent`, после истечения lease письмо может быть отправлено повторно. Стабильный Message-ID помогает почтовой инфраструктуре распознать повтор, но не гарантирует его подавление.

Dispatcher запускается при старте Express, после обработки платёжного webhook и раз в минуту, пока процесс работает. Это не отдельный постоянно работающий worker: Render Free может приостанавливать сервис, поэтому повторная отправка может задержаться до следующего запуска или входящего запроса. Для гарантированного SLA нужен постоянно работающий worker либо внешний scheduler; они пока не настроены. Если SMTP не сконфигурирован, dispatcher не забирает события из очереди и не расходует попытки.

Тесты `backend/test/postgres-integration.sql` проверяют создание ровно одного события при активации, отсутствие второго события при повторном вызове и fencing по claim-токену. `backend/test/subscription-concurrency.sh` запускает две отдельные PostgreSQL-сессии для проверки конкурентной активации. CI должен применить миграцию 030 перед этими тестами.

До применения миграции 030 и backend-деплоя старое поведение продолжает действовать. Новая схема и код находятся только в feature branch; production база и сервис не изменялись.

### Валюта в уведомлении Prodamus

В опубликованном Prodamus примере вебхука и перечне его параметров есть `sum`, но нет отдельного поля валюты. Поэтому backend сверяет сумму с валютой и суммой, сохранёнными во внутреннем заказе при его создании; валюту из уведомления не выводит и не угадывает. Это важно для международных платежей: валюта заказа берётся из выбранного тарифа (`rub` или `usd`), а не из локали пользователя или страны его карты. Если Prodamus изменит состав уведомления или начнёт передавать валюту, её проверку следует добавить отдельным изменением и покрыть тестами.

### Формат запроса к платёжной форме

Позиции заказа передаются как вложенные form-urlencoded поля, например `products[0][name]`, `products[0][price]`, `products[0][quantity]`. Backend сериализует вложенные массивы и объекты в bracket notation; JSON-строка в поле `products` не используется. По документации Prodamus подпись исходного payload рассчитывается как HMAC-SHA256 от канонической JSON-строки (значения строками, ключи рекурсивно отсортированы, `/` экранируется) и передаётся в поле `signature` тела запроса в hex. Заголовок `Sign` используется для обратного вебхука, а не вместо поля `signature` при создании ссылки.
